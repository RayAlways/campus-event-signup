### Story 2.1: 先到先得报名并查看本人结果

As a 已登录、希望参加活动的同学，
I want 在报名期内报名先到先得活动，并查看本人是否成功入名单，
So that 能根据服务端的真实结果安排参与，而不是把点击按钮当作获得名额。

本文件保留已批准审阅快照。用户于 2026-11-27 回复“通过”，批准 Story 2.1 及自报名建议（D-023）；正式维护入口为 epics.md，本文件不再独立演进。实施以前五条故事为基础；活动保持既有设置，不依赖未来参加审核、退出、模式切换、候补或通知代码。规范获批不等于实现或测试完成，不直接标为 ready-for-dev。

**已确认 S-1（D-023）：允许发起者手动报名自己的活动，遵守相同时间、容量和重复规则，占一个正常名额；发布不自动报名。**审核模式下也须提交并审核自己的参加申请，不因发起者身份自动通过；实际审核场景由后续故事承接。PRD 已同步关闭自报名保留项，名单字段等其他保留项不因此关闭。

**Acceptance Criteria:**

#### AC-2.1-01 有名额时真实报名成功

**Given** 用户已登录并取得有效 CSRF 令牌，目标为已发布的先到先得活动，处于报名窗口且未持久关闭报名，本人没有当前有效申请，并有可分配名额，
**When** 在详情页提交报名，服务端在统一活动事务中受理，
**Then** 返回 HTTP 201、报名尝试字符串 ID、CONFIRMED 状态及版本；创建或使用本人的唯一参与槽位，并将当前指针指向此次尝试，
**And** 服务端保存原始受理时间和活动内唯一受理序号，不接收客户端伪造的申请时间、状态、用户或队列位置，
**And** 已占人数增加恰好一人，公开详情按真实记录计算剩余名额；报名不提升活动配置版本，不自动创建退出请求或变更通知。

#### AC-2.1-02 时间与模式条件在实际受理时检查

**Given** 页面可能已过时，活动可能尚未开放、已截止、已开始、未发布，或当前采用参加审核模式，
**When** 提交新的先到先得报名命令，
**Then** 报名开始时允许、截止时及以后禁止，即报名开始≤服务端时间＜截止，且不能绕过已保存的报名关闭事实，
**And** 已发布但时间/模式不符返回 409 和具体业务原因；未发布或不存在按公开不可见约定返回 404，不能偷读草稿，
**And** 先取得活动行锁，再以独立 SQL 读取数据库 UTC 时间；分配名额前和最终写入前重新核对适用边界，跨截止时整条命令回滚，不使用浏览器时间或等待锁前的旧时间放行。

#### AC-2.1-03 满额失败与最后名额竞争

**Given** 活动已满，或多个不同用户竞争最后一个名额，
**When** 并发提交报名，
**Then** 最多一个用户新增成功记录，其余返回 409 CAPACITY_FULL；不出现负剩余人数、超过容量或失败者的有效报名，
**And** 满额失败不自动加入候补、不产生待审申请，也不保存“报名成功”的历史；页面显示真实失败并刷新名额，
**And** 按统一活动根行锁、同一 Spring JDBC READ_COMMITTED 事务计数和写入，CONFIRMED 记录数为名额真值，不引入第二份可写人数。

#### AC-2.1-04 同人并发和网络重试不重复占位

**Given** 用户双击、两个页面同时操作，或提交成功后响应丢失，
**When** 以相同或不同幂等键再次提交，
**Then** 同一用户同一活动最多一条当前有效申请，已有成功记录时不同键报名返回 409 ALREADY_PARTICIPATING，并提示读取本人当前状态，
**And** 身份/目标权限校验后，同键同载荷成功回执先于新的状态/时限检查重放原结果；即使后来已截止，也只重放而不重新占位；同键不同目标/载荷返回 409，
**And** 回执与报名同事务保存；跨活动复用键的唯一冲突须回滚后核对原回执，不造成两次报名。重放后页面重新读取当前状态，不能将历史成功回执当作永久有效资格。

#### AC-2.1-05 本人状态可独立查询与刷新

**Given** 用户可能尚未报名，或已通过本故事成功报名，
**When** 详情加载、刷新、报名返回后或网络结果不确定时读取本人在该活动的当前参与状态，
**Then** 未报名返回 HTTP 200 和明确的无当前申请结果；已成功返回本人 CONFIRMED、尝试 ID、版本、受理时间及活动退出策略，
**And** 页面展示“报名成功”，刷新或重新登录后仍可查，不能仅依赖本地变量或 toast 维持结果，
**And** 本故事只提供当前活动的本人最小状态入口；跨活动“我的报名”、完整尝试历史和后续状态增量由对应故事承接，不等待它们才能确认本次结果。

#### AC-2.1-06 身份隔离与发起者自报名

**Given** 匿名用户、另一用户或活动发起者尝试报名/读取个人状态，
**When** 服务端处理请求，
**Then** 身份仅取会话，不允许用 userId/actorId 代别人报名；非法身份/状态控制字段返回 400，其他人的尝试、名单和秘密不出现在响应中，
**And** 有效 CSRF 的匿名写请求及匿名个人查询为 401，缺少/伪造 CSRF 的写请求为 403，公开活动读取仍无需登录；私人响应使用 no-store，
**And** 按已确认 S-1（D-023），发起者手动报名自己的活动时也须有名额且处于报名期，成功后占一个名额，无自动报名或额外名额；本项仍待实际测试，规范获批不等于软件验收通过。

#### AC-2.1-07 基础设施失败不留下部分结果

**Given** 事务写入或回执保存出错、发生死锁/锁超时，或客户端没有收到明确响应，
**When** 回滚并重新查询或使用原幂等键重试，
**Then** 失败不留下部分尝试、当前指针、序号更新或成功回执，已确认的旧数据不受损；基础设施失败为可重试 503，不泄露 SQL 及连接信息，
**And** 页面明确区分“失败”和“结果暂未确认”，先查询本人状态再按原键重试，不凭超时宣称已成功或另开第二次占位，
**And** 重试重新取锁、取时并核对资格，不能因先前请求曾进入系统而绕过截止。

#### AC-2.1-08 正常重启保留报名事实

**Given** 多名用户已取得成功报名响应，
**When** 刷新页面或正常停止并重启应用，必要时重新登录，
**Then** 原活动、参与槽位、尝试 ID、状态、原始时间/序号和成功回执保持，当前成功人数与公开名额一致，
**And** 不以演示数据重建、清空业务表或持久化登录会话来替代业务数据持久性，
**And** 活动即使已经截止或开始，成功记录仍可查，不能把时间推进误作丢失或自动退出。

#### AC-2.1-09 独立交付与实际证据

**Given** 仅 Epic 1 和本故事已实施，尚无后续审批、退出、候补、模式修改及通知能力，
**When** 用浏览器和真实 MySQL 验证报名及本人结果，
**Then** 保存合法报名、满额、边界、最后一席竞争、同人竞争、同/异键重试、权限、回滚及正常重启的实际证据，并回归前五条故事，
**And** 基于 Story 1.5 已有最小关系做所需增量迁移，只补当前指针、受理时间/序号、唯一约束及回执等确需字段；不预建退出、通知或全部未来状态处理流程，
**And** 并发测试使用独立测试库，实际请求数、轮次和环境须记录；A-6 的 50 请求/20 轮仍待确定，不把建议预算或 SQL 夹具写成实测，
**And** 不开放虚假的审核/退出入口，也不宣称完整 FR-15、未来队列公平性或其他未实施流程已验收。

#### 已确认的接口与阶段边界

| 接口 | 本故事用途 |
|---|---|
| POST /api/activities/{activityId}/registrations | 当前先到先得报名；会话身份、Idempotency-Key，无客户端身份/状态/时间字段；首次 201 |
| GET /api/activities/{activityId}/my-participation | 登录后读取本人在该活动的最小当前状态；无当前申请为 200 空状态；不接收他人 userId |

精确字段和错误码须先进入共同接口契约，再由两位成员核对后并行实施。后续审核模式扩展同一报名端点的状态分支，不另建可绕过模式的“直接通过”接口。错误、BIGINT 字符串、UTC 时间和前端北京时间显示沿用 AD-7。

本故事在固定设置下不产生候补，不提前完成 FR-23。Epic 3 必须在开放模式迁移的同一增量中，将此报名入口接入旧候补优先逻辑，并回归新报名不能插队；不能先开放模式切换，再留待未来修补公平性。待审/退出历史等状态随真正的写故事扩展，当前仅建立必要的 CONFIRMED 路径。
