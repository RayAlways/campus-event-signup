### Story 2.3: 发起者查看参加申请和当前成功名单

As a 活动发起者，
I want 查看自己活动的参加申请、待审人数和当前成功名单，
So that 能区分申请与实际参加者，掌握真实名额，为后续审核提供依据。

本稿待审。D-024 仅批准 Story 2.2，不批准本稿或关闭 A-5。前置为已经批准的七条规范；实施按其顺序完成，本故事利用现有 PENDING/CONFIRMED 记录即可独立读取，不等待未来参加/退出审核、重报或模式迁移才能工作。

**待确认建议 A-5：当前成功名单的用户可见字段只包括用户名、昵称、报名状态。**申请记录另显示原提交时间以辅助审阅；接口为后续操作提供尝试 ID、版本等必要技术标识，但不因此显示账号秘密、手机号、学号、邮箱或退出理由。本次不增加导出或批量审核功能。用户批准前，PRD 的 A-5 继续保持待复核。

**Acceptance Criteria:**

#### AC-2.3-01 本人活动可进入申请与名单视图

**Given** 当前用户已登录，目标活动由其发起并已经发布，
**When** 从本人活动管理入口打开参加管理页，
**Then** 页面可查看“申请记录”和“当前成功名单”，显示目标活动标题、模式、容量、待审核人数和成功人数，数据来自本人活动的真实记录，
**And** 在既有活动详情中为本人提供参加管理入口，服务端仍独立核对归属，不依赖未来“我发起的全部活动”列表才能打开，
**And** 没有申请时返回 HTTP 200、空集合和零人数，显示明确空状态，不使用虚构示例填充，
**And** 本故事只提供读取，不放置尚未实现的通过、拒绝、退出审核、取消或导出按钮来伪装流程完整。

#### AC-2.3-02 申请记录与当前状态不混淆

**Given** 活动存在此前通过 Story 2.1/2.2 受理的申请，未来也可能通过对应故事产生终态历史，
**When** 发起者读取该活动的申请记录，
**Then** 每条真实尝试独立列出用户名、昵称、该次报名状态及原提交时间；当前有效尝试与历史尝试明确区分，同一人的多次尝试不覆盖或合并成一次，
**And** 当前 PENDING 明确为“待审核、尚未报名成功”，CONFIRMED 为成功；未来拒绝、撤回、退出状态须随其真实写故事增量接入，不把未实施状态造入生产数据，
**And** 接口提供该次尝试的字符串 ID、版本和当前标记，为后续审核定位该次记录，不能只用用户 ID 代表任意一轮报名；读取不产生审核结果。

#### AC-2.3-03 成功名单只包含真实占位者

**Given** 同一活动可能有成功、待审及非成功历史记录，
**When** 查看当前成功名单，
**Then** 名单只包含当前有效且状态为 CONFIRMED 的报名，每人至多一行；PENDING、未来候补及已拒绝/撤回/退出记录不进入成功名单，
**And** 按待确认 A-5，用户可见字段仅用户名、昵称和报名状态，不展示密码、编码值、会话、私密账号资料或退出理由，
**And** 已确认的“退出待审仍成功占位”规则保留；实际退出请求尚未实施，本故事不创建退出表或声称该联动已验证，后续退出故事须使其继续在名单中并补充准确状态提示。

#### AC-2.3-04 人数与名额来自同一一致快照

**Given** 读取期间可能有其他用户提交申请或报名，
**When** 服务端构建一次参加管理响应，
**Then** 成功人数等于该快照中的成功名单行数和 CONFIRMED 数，待审核人数仅计当前 PENDING；容量、已占与剩余满足剩余＝容量−成功人数，
**And** 申请历史总条数不能作为成功人数或待审人数，不把重报历史重复计入当前人数，
**And** 以同一数据库一致快照读取容量、汇总与对应集合，不能拼接不同查询时点造成同一次响应人数与名单矛盾；不引入独立可写人数计数器，
**And** 公开活动与管理页若在不同请求时点读取可以因真实并发而不同，不能用缓存旧数据宣称同时一致；刷新后按各自真实快照呈现。

#### AC-2.3-05 资源权限在服务端检查

**Given** 匿名访问者、普通参与者、另一活动发起者，或本活动发起者本人直接请求接口，
**When** 读取目标活动的申请、成功名单和管理汇总，
**Then** 匿名请求为 401；其他登录用户读取公开已发布活动的管理数据为 403，不能因知道活动 ID、参加过活动或能管理别的活动而越权，
**And** 不存在或对请求者不可见的草稿为 404；本人草稿不接收报名，管理读取返回 409 ACTIVITY_NOT_PUBLISHED，而不是伪装成可报名活动，
**And** 身份及发起者归属只取会话和数据库，不接受 ownerId/actorId 绕过检查；拒绝响应不夹带他人名单或申请，
**And** 精确公开活动 GET 接口继续只返回公共字段，不能为方便复用而将名单、申请和私人汇总并入公开详情。

#### AC-2.3-06 原始顺序和时间边界不触发写入

**Given** 活动处于报名中、已截止或已开始阶段，且记录仍保留，
**When** 查看申请与名单，
**Then** 本稿建议申请记录与成功名单均按原提交时间升序、同刻按活动内受理序号数值升序稳定排列，由服务端排序，
**And** 该显示顺序不是审核模式的自动批准或强制先进先出规则；不因排在前面就生成成功资格，
**And** 截止或开始后仍允许发起者读取；开始后待审保留并提示“处理已截止”，不自动批准、拒绝、删除或重排原申请时间，
**And** 时间取服务端，显示沿用北京时间；首次版本不增加筛选或分页，未来如增加分页必须先全局稳定排序。

#### AC-2.3-07 只读、隐私和失败状态真实

**Given** 请求成功、网络失败、身份过期或数据库查询失败，
**When** 页面加载或刷新参加管理数据，
**Then** 显示对应加载、空、拒绝或失败状态，失败不显示为“无人报名”，也不将上一活动的名单留作当前活动结果，
**And** 私人接口及页面数据响应使用 no-store，退出登录或切换用户时清除先前私人视图；不在日志记录账号秘密或退出理由，昵称等内容按纯文本呈现，
**And** 读取路径保持只读，不修改活动配置、尝试版本、当前指针、受理时间、名额或回执，不以查询触发自动通过或补录，
**And** 基础设施失败按既有 503 约定返回，不泄露 SQL；重试仅重读，不要求为 GET 新建幂等回执。

#### AC-2.3-08 刷新与正常重启保留真实视图

**Given** 用户已通过前置故事保存报名和待审申请，
**When** 刷新或正常重启后重新登录查看，
**Then** 原有申请 ID、时间/序号、当前状态及其对应名单和人数保持，页面不回到演示数据或依赖浏览器本地缓存，
**And** 查询本身不新增或丢失数据，阶段提示随真实时间推进，不能将提示变化误作申请状态被改写，
**And** 注册、草稿、发布、公共浏览、两种报名与本人状态读取仍可用，未为管理视图扩大公开权限。

#### AC-2.3-09 独立验证与后续增量边界

**Given** 前七条规范与本故事按顺序实施，而未来审批、退出、重报、迁移和取消尚未实现，
**When** 使用真实页面及 MySQL 验证管理读取，
**Then** 保存空视图、两个模式下已有记录、归属隔离、最小字段、稳定排序、并发读取快照、截止/开始后读取、错误提示及正常重启的实际证据，
**And** 尚无业务写入口的终态/多次尝试可用仅限独立测试库的 SQL 夹具验证查询，但必须标明夹具，不能冒充真实审核、撤回、退出或重报已经工作，
**And** 只增加当前查询确需的索引和投影，不预建审核流水、退出请求、变更或通知表，不用未来故事代码作为前置，
**And** 当前为待审规范，A-5 和显示顺序需用户批准，运行结果尚不存在，不直接标记 ready-for-dev 或课程软件验收通过。

#### 读取契约建议

建议采用 `GET /api/activities/{activityId}/participation-management` 返回同一快照的活动基本字段、汇总、申请集合与成功名单；前端可用两个视图切换，避免分别请求再拼接出不同快照。精确字段、索引和快照实现方式在共同契约中固定，由两位成员核对后实施。

成功名单显示用户名、昵称和报名状态；申请记录另显示原提交时间。尝试 ID、版本、当前标记、排序键等接口元数据只为准确关联与后续操作使用，不放大用户可见账号资料范围。所有 BIGINT 标识/序号用十进制字符串，前端不得字符串重排；响应和 HTTP 约定沿用既有契约。

后续参加审核在本页接入真实操作，退出待审状态提示随退出故事接入；重报时保持每次尝试及当前指针语义，候补/取消的读取增量在 Epic 3 随相应写入口共同交付。此故事不公开名单、不新增审核标准，不把只读页面当成审核流程完成。
