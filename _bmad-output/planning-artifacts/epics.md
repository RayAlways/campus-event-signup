## Requirements Inventory

### Functional Requirements

以下保持 PRD 的原编号；每条摘要包含影响后续故事和验收的主要规则。完整业务依据仍为 PRD，不以摘要删减源文。

- **FR-01：注册与登录。**唯一用户名、昵称和密码注册；重复用户名、缺项或错误凭据不建立登录状态。任何已注册用户均可创建活动，不需申请组织者资格；第一版不要求手机号、学号或实名资料。D-017 已确认 Story 1.1 的用户名标准化与字段/密码输入边界，详见正式故事；后续登录不得另起一套用户名处理方式。
- **FR-02：退出登录。**退出后原凭据不能继续执行需登录的写操作；旧页面不能绕过服务端身份检查。
- **FR-03：创建和修改草稿。**登录用户只能创建、读取和修改自己的草稿，草稿不公开、不接受报名。D-019 已确认允许不完整暂存，已填容量须为正整数，已填相关时间须满足先后关系，字段、文本长度和可选结束时间见正式 Story 1.3；发布必填及当前时间条件已由 D-020 确认，见正式 Story 1.4。
- **FR-04：发布及报名模式。**发起者发布合法草稿，选择先到先得或发起者审核；D-020 已确认发布必填项、截止须在未来及最小公开详情。发布后在允许时限内可修改模式，须说明、通知，并按 FR-23 迁移申请，不能仅改字段。
- **FR-05：列表与详情。**未登录可浏览公开活动、模式、时间及真实名额，不公开完整名单。D-021 确认发布时间/ID 数值倒序，保留各时间阶段活动及结束展示，初版不加搜索/筛选/分页。取消活动仍在列表且统一沉底、标“活动已取消”，详情/原因/历史可查、报名关闭，随 Epic 3 接入；若以后分页，先全局排序再分页。
- **FR-06：修改已发布活动。**仅发起者修改本人活动，变更说明必填，非法修改不产生成功通知；不清退名单或删除历史，容量不得小于成功名单人数（含退出待审者）。开始前可改时间、容量、模式和退出策略；已截止报名不因改期重开。开始后仅可改标题/说明/地点等普通信息及公告，不能改业务设置或取消整场；实际生效时检查时限。
- **FR-07：先到先得报名。**D-023 已确认允许发起者手动报名自己的活动，同样占位并遵守规则，发布不自动报名；审核模式不自动通过。登录用户仅在报名期内报名；有名额且已处理应优先补录的旧候补才成功。满额失败，不新增成功记录；新报名不能插队，同一人不得重复产生有效申请或占位。
- **FR-08：提交参加审核申请。**D-024 已确认 Story 2.2 的提交/本人读取、模式意图校验及待审过期提示约定。报名期内提交后为待审核，不占名额；满额仍接收待审申请。截止后不接收新申请，也不删除已有申请；释放名额不使审核模式申请自动通过。
- **FR-09：发起者查看申请。**D-025 已确认申请字段、原提交时间升序和私人一致快照读取；显示顺序不强制审核先后。仅查看自己活动的申请及状态；待审与成功人数分别展示，候补按有效顺序展示，不能把申请总数当成功人数。
- **FR-10：审核通过参加申请。**D-026 已确认 Story 2.4 的尝试/版本定位、容量并发与审核结果最小查询；当前审核模式下，发起者可在活动开始前处理截止前提交的待审申请；有名额才通过，满额失败仍待审。并发通过不超容量；先到先得模式不开放人工插队通过入口。
- **FR-11：拒绝参加申请。**当前审核模式、审核期内仅发起者可拒绝；拒绝不占名额，理由选填，本人可见结果。D-026 已确认纯文本理由去首尾空白后最多 500 个 Unicode 码点，空白按未提供，仅本人及发起者可读。不能用“拒绝参加”移除已成功者，后者须按退出流程处理。
- **FR-12：撤回未入名单申请。**D-027 已确认 Story 2.5 的本人待审撤回、审核竞争及最小结果读取，候补增量仍在 Epic 3。活动开始前，本人可撤回待审或候补，报名截止后也可撤回；不改变已占名额，撤回记录不再被审核或补录。并发录入若先成功，就按已入名单者的退出策略处理。
- **FR-13：已入名单者退出。**D-028 已确认 Story 2.6 的两种报名来源自由退出、一次释放与结果读取，候补/策略变更增量仍在 Epic 3。开始前按独立退出策略处理：自由退出直接生效，受限退出须提交理由并获批。真正退出才移出名单并释放一次名额；当前先到先得且有旧候补则按序补录，审核模式不自动通过申请，报名截止不因此延长。
- **FR-14：再次报名及历史。**被拒、撤回或退出后，在仍开放的报名期内可重新申请，保留旧历史，按当前模式和新申请时间处理；不恢复旧排队位置。每人每场最多一条当前有效申请；退出待审仍属成功，不能再占一位。
- **FR-15：本人记录与状态。**本人可查看活动、申请及结果；待审/候补明确提示尚未成功，退出待审同时显示“报名成功、退出待审核”。开始后未处理的申请仍可查并提示处理已截止，不自动批准或递补。
- **FR-16：成功名单。**仅发起者可查看本人活动的成功名单，包含退出待审者，排除未入名单和已经退出者，人数与占位一致；不显示密码等私密账号信息。D-025 已确认最小字段为用户名、昵称和状态，A-5 已关闭；名单不公开。
- **FR-17：重复请求与失败反馈。**重复点击或重试不重复申请、占位、释放或通知；失败不产生部分业务变化。未登录、无权、过期、状态冲突或容量不足有明确结果；冲突时返回当前状态并要求刷新，不把失败显示为成功。
- **FR-18：设置退出策略。**退出策略独立于报名模式，两种模式×两种退出策略的四种组合均须可用；详情和本人页面显示退出条件。开始前可改策略，保留既有申请；改自由退出后本人可直接退出，旧请求不能再次释放名额；开始后策略固定、退出关闭。
- **FR-19：退出申请与审核。**D-029 已确认 Story 2.7 的提交/撤回与私人读取，退出理由纯文本、去首尾空白后 1–500 个 Unicode 码点。受限退出须在开始前提交必填理由，仅本人和发起者可见理由及结果，仅发起者审核。待审仍成功占位；通过才退出，拒绝不释放。开始前可撤回待审退出申请，被拒后可重提，不能有并行有效请求；开始后停止提交、撤回和审核，历史保留，不自动退出。
- **FR-20：活动公告。**仅发起者发布/修改本人活动公告；包含正文与发布时间，更新需说明并按 FR-21 通知，保留变更记录，第一版不硬删除。开始后仍可发布和更新公告。
- **FR-21：站内通知。**活动修改/公告更新或取消须说明，向变更前成功名单生成通知，含退出待审者，不含仅待审/候补者。登录后查看，有未读提示；通知包含活动、类型、说明、时间和入口。每次变更每人最多一条，仅能读和标记本人通知；已读不删除事实，也不代表重新同意变更。取消后仍能读取和标记已读；不要求外部渠道或实时推送。
- **FR-22：整场取消。**仅发起者在开始前填原因取消本人已发布活动；关闭待审参加、候补和待审退出请求，标“因活动取消关闭”，停止报名、参加/退出审核、个人撤回/退出和补录。成功历史不记作主动退出；活动及通知保留，列表沉底。开始时及以后禁止取消；重复取消不重复通知。
- **FR-23：模式切换与公平补录。**审核转先到先得时，成功者不变，有效旧待审按原申请时间优先录入，满额剩余转有序候补；同时间按服务端受理顺序。先到先得切回审核，成功者不变，候补转待审并保留原时间，停止自动通过。自由退出、退出获批或扩容释放名额时，当前先到先得优先补录旧队首，新申请不能插队。开始前可补录，截止后仅处理已有候补；开始/取消后停止。重报用新时间，失效历史不复活，改期不重开截止报名，反复切换不重置有效队列键。

### NonFunctional Requirements

- **NFR-01：名额与状态一致性。**成功响应后始终满足已占人数＝成功名单人数、剩余名额＝容量−已占人数≥0；失败无部分扣位或半成功。验证覆盖最后一席的并发报名/通过，及撤回、切换、补录、退出批准、扩容、取消交错；超额、负数、重复占位/释放、违反旧申请优先的次数目标均为 0。50 并发请求、每模式 20 轮仍是 A-6 验证预算建议，执行前由两位成员确定并记录环境、实际请求、轮次和失败响应，不声称已经测试。
- **NFR-02：身份与资源隔离。**不得明文存储密码或向日志/接口/名单泄露密码；注册登录不获得他人活动管理权。用未登录、参与者、本活动发起者、他活动发起者验证允许/拒绝路径；未经授权写入和他人私密记录泄露目标均为 0。覆盖退出理由、通知、名单与公告管理；退出后旧凭据不能继续写入。
- **NFR-03：正常重启持久性与可复现。**已成功返回的账号、活动、申请和审核、队列顺序、取消及通知已读状态，刷新或正常停止/重启后保留；不能恢复成初始演示数据。保存多状态数据重启比较，由另一成员从干净检出按 README 初始化、启动及验证；异常断电恢复未纳入本次确认范围。
- **NFR-04：变更与通知一致性。**不能变更成功却漏掉原成功名单的通知；失败操作不能生成成功通知，同变更同接收者至多一条，取消原因入口保留。以成功者、退出待审者、参加待审者和候补者验证接收者集合、归属、数量、说明、未读及跨用户隔离；漏通知、重复通知及泄露目标为 0。

### Additional Requirements

AR 编号仅用于本规划中的架构输入追踪，不替代 FR/NFR，不增加用户已批准的业务范围。除 AR-01 中已选高层技术组合外，下述实现机制来自 draft 架构，属于 T-1/T-2 技术建议；故事进入实施前须明确采用状态。

- **AR-01：官方 Starter 及版本种子。**后续首个基础搭建故事应以 Spring Initializr 和 create-vue 为起点。架构已核查 Boot 4.2.0、Java 编译目标 21、Vue 3.5.46、Router 5.5.1、Vite 8.3.8、MySQL 8.4.13.1 等种子；详细版本、BOM、Wrapper 和来源以架构 Stack、version-research.md 为准。实际 JDK 补丁、数据库供应与构建尚未验证，不能把核查写成已安装。
- **AR-02：单体及模块边界（AD-1）。**Vue `/api`→Spring MVC JSON→后端规则；一个应用、一个业务数据库，按 identity/activity/participation/notification 分模块，由应用层协调；前端不裁决身份、名额或时限。
- **AR-03：统一事务和名额真值（AD-2）。**已存在活动的全部业务写先锁活动主键行，同一 Spring JDBC READ_COMMITTED 事务中检查、计数和变更；不独立提交、不持锁调外部服务。名额由 CONFIRMED 计数，不另设可写人数真值；读取容量与人数采用一致快照。
- **AR-04：当前槽位与历史（AD-3）。**活动/用户唯一槽位指向当前报名尝试，重报新建 attempt；退出请求独立，待审不改成功状态。保持指针归属、唯一性和终态不复用；整场取消保留成功历史，未处理请求按取消关闭。
- **AR-05：时间、队列和截止事实（AD-4）。**锁后另取数据库 UTC 时间，分配及最终写前复核，跨适用时限整条回滚；队列键为原提交时间＋活动内受理序号。切换/扩容/真实退出在事务内同步补录，禁止新申请插队；持久保存截止事实，编辑不清除。
- **AR-06：Session、CSRF 与资源权限（AD-5）。**服务端会话、HttpOnly/SameSite Cookie，HTTPS 时 Secure；登录轮换、退出失效，保留 CSRF，密码单向编码。身份取会话，按 owner/user/recipient 校验资源，不采信客户端 actorId；公告与说明按纯文本展示。
- **AR-07：通知同事务（AD-6）。**先快照原成功名单，再写变更、不可变历史与去重站内通知；失败整体回滚，不仅依赖提交后异步监听。通知不含退出私密理由；已读只影响本人通知。
- **AR-08：基础接口契约（AD-7）。**状态枚举统一，JSON camelCase，BIGINT 标识/序号传字符串，UTC ISO-8601 时间、页面北京时间；统一成功/错误结构和实际 HTTP 状态，不能由前后端分别发明字段或状态。
- **AR-09：版本与幂等（AD-7）。**编辑和已有申请操作核对对象版本；活动命令成功回执与业务同事务，按用户＋幂等键唯一。同键同载荷重放、不同载荷拒绝，旧请求不影响新 attempt；失败/锁超时/死锁不留下部分变更，重试重新检查时限。
- **AR-10：迁移及持久化（AD-8）。**Flyway 是结构迁移入口，不改写已共享迁移；MySQL 保存业务，启动不清表或覆盖演示数据；开发/测试数据库分离。

## Epic 1: 进入系统并发布、发现活动

目标：同学可以建立身份，组织者可以保存、发布活动，同学可以浏览活动及参与条件。本节的 5 条故事规范均已审阅通过，当前没有实施或运行测试结果。

### Story 1.1: 通过网页注册账号

As a 班级或社团的同学，
I want 通过网页填写用户名、昵称和密码，创建自己的账号，
So that 后续可以登录并以本人身份发起或参加活动。

本故事规范已于 2026-11-27 获用户批准（D-017），当前尚未实施或测试。首次基础搭建采用已核查的官方 Spring Initializr / create-vue，必须交付可实际注册的页面与持久化接口；不只交付空项目，也不预建全部业务表。注册结果在本故事内即可验证，不依赖后续登录故事。

**Acceptance Criteria:**

#### AC-1.1-01 从干净检出启动真实注册页面

**Given** 仓库按本故事生成最小 Vue、Spring Boot 项目，并准备了文档指定的 JDK、Node 和真实 MySQL 环境，
**When** 开发者从干净检出目录按 README 的实际步骤初始化数据库并启动，
**Then** 浏览器能打开真实注册表单，包含用户名、昵称和密码输入及提交入口，
**And** 页面调用本项目后端，连接真实 MySQL；不是 Mock 返回或静态“注册成功”，
**And** 所有必需配置均提供不含真实凭据的示例，README 命令须由本故事执行验证后填写，不把计划命令写成已经验证。

#### AC-1.1-02 合法输入创建一个普通账号

**Given** 注册用户未登录，已经按同源 CSRF 流程取得令牌，且标准化后的用户名尚不存在，
**When** 提交符合本故事输入约定的用户名、昵称和密码，
**Then** 后端返回 HTTP 201 和统一 JSON 成功结构，数据库恰好新增一个用户，
**And** 返回的 ID 为字符串，响应只包含必要的账号标识、用户名和昵称等公开结果，不含密码或密码编码，
**And** 页面显示明确的注册成功结果；本故事不自动登录，也不依赖尚未实现的登录入口来证明注册成功，
**And** 账号不要求手机号、学号、实名或组织者资格申请；客户端传入额外角色标记不能获得管理员或管理他人活动的权限。

#### AC-1.1-03 无效输入不产生账号

**Given** 有有效 CSRF 令牌，但至少一个必填字段缺失、为空白或不符合下述输入约定，
**When** 用户通过页面提交或直接请求注册接口，
**Then** 后端返回 HTTP 400 和可定位的字段错误，用户表没有新增记录，
**And** 页面保留可修正的用户名和昵称并显示失败原因，不展示成功或跳转到未实现页面，
**And** 仅绕过前端校验不能注册不合法账号；密码不自动裁剪、去空格或静默截断。

#### AC-1.1-04 重复或并发重复注册不能产生两个账号

**Given** 相同标准化用户名已存在，或两个请求同时尝试注册该用户名，
**When** 依次提交或并发提交这两个请求，
**Then** 已存在时返回 HTTP 409；并发首次注册时至多一个请求创建成功，其余返回明确的用户名冲突，
**And** 数据库用户名唯一约束仍成立，没有第二个同名账号，也不向客户端返回 SQL 或堆栈详情，
**And** 重试不能覆盖原账号的昵称或密码。注册依靠唯一用户名处理重复，不为此预建活动命令回执表。

#### AC-1.1-05 密码与注册日志不泄露秘密

**Given** 注册请求携带一个可识别的测试密码，
**When** 分别验证注册成功、字段错误、用户名冲突和服务端失败路径，
**Then** 所有响应及应用日志都不包含测试密码或密码编码，数据库只保存单向密码编码，
**And** 使用本故事配置的 PasswordEncoder 能验证原密码、拒绝错误密码，不使用明文或可逆存储，
**And** 配置与日志不提交真实数据库凭据、CSRF 令牌或会话标识。

#### AC-1.1-06 同源会话与 CSRF 在未登录注册时也有效

**Given** 注册页面从本应用来源访问 `/api`，
**When** 用户先获取 CSRF 令牌，再携带对应会话 Cookie 和 `X-CSRF-TOKEN` 注册，
**Then** 正常注册路径可以完成，
**And** 缺少或伪造 CSRF 令牌的写请求返回 HTTP 403，且不创建账号，
**And** 会话 Cookie 为 HttpOnly、SameSite=Lax，HTTPS 配置启用 Secure；开发通过 Vite 代理，不能靠全局关闭 CSRF 或放开任意来源解决联调。

#### AC-1.1-07 正常重启保留账号

**Given** 一个账号已注册成功，
**When** 正常停止并重启后端，再尝试注册相同标准化用户名，
**Then** 原用户及密码编码仍存在，重复注册仍被拒绝，不回到初始空数据，
**And** 前端刷新也不会再次自动提交注册或误报成功。

#### AC-1.1-08 只创建当前需要的结构并保留复现证据

**Given** 本故事是首个实施单元，
**When** 检查提交的迁移、源代码、启动记录与测试结果，
**Then** 业务迁移只包含当前账号所需表和唯一性约束；Flyway 自身元数据不算额外业务表，
**And** 未提前创建活动、报名、候补、退出、变更、通知或活动命令回执表，
**And** 保留真实 MySQL 上注册成功、无效输入、重复/并发重复、CSRF、密码保护及重启的验证结果，并记录实际环境与失败响应，
**And** 没有实现后续活动或报名功能，没有把本故事的账号并发验证当成 NFR-01 最后名额验证已完成。

#### 本故事的输入约定（2026-11-27 已确认）

以下接口和存储输入约定已由用户在本次审阅中确认，并同步回 PRD 的 FR-01：

| 字段 | 已确认约定 |
|---|---|
| 用户名 | 去首尾空白后为 3–32 个英文字母、数字或下划线；按小写标准化后保存并判重，因此 Alice_01 与 alice_01 不能注册为两个账号 |
| 昵称 | 去首尾空白后为 1–32 个 Unicode 码点，支持中文；不要求唯一 |
| 密码 | 不全为空白，至少 8 个 Unicode 码点，UTF-8 编码至多 72 字节；保存前不裁剪或改变原值，超限明确拒绝，不静默截断 |

密码的字节上限配合本故事采用的 BCrypt 注册侧编码方案；此确认仅承接本故事展示的范围，不把架构全部机制和环境可用性一并标为通过。若后续调整输入约定，先记录变更并更新正式故事及接口约定，再实现与测试，不由前后端各自猜测。

72 字节限制已核对 [OWASP 的 BCrypt 输入说明](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#input-limits-of-bcrypt)，编码器能力见 [Spring Security API](https://docs.spring.io/spring-security/reference/api/java/org/springframework/security/crypto/bcrypt/BCryptPasswordEncoder.html)。用户名/昵称长度与密码最少 8 个码点是本项目本次确认的输入约定，不是这些文档规定的默认产品规则。

### Story 1.2: 登录并安全退出登录

As a 已经注册的同学，
I want 使用自己的用户名和密码登录，并在使用后退出，
So that 系统能够识别本人，且退出后的旧凭据不能继续访问需登录的能力。

本故事规范已于 2026-11-27 获用户批准（D-018），尚未实施或测试。唯一前置故事为 1.1；通过当前身份接口和测试作用域受保护处理器即可独立验证会话，不依赖未来的活动、报名或管理接口。用户名和密码沿用 D-017 已确认的处理方式。

**Acceptance Criteria:**

#### AC-1.2-01 正确凭据建立可用会话

**Given** 用户通过 Story 1.1 注册，当前未登录，并取得与当前匿名会话对应的 CSRF 令牌，
**When** 通过登录页面提交正确用户名和原密码，
**Then** `POST /api/auth/login` 返回 HTTP 200 和统一 JSON 成功结果，建立本人服务端会话，
**And** 用户名按已确认方式去首尾空白并转小写查找；密码按原值验证，不裁剪、转大小写或截断，
**And** 登录时轮换此前匿名会话标识；紧接着用当前 Cookie 请求 `/api/auth/me` 能返回同一用户的字符串 ID、用户名和昵称，不能只在登录那一个请求内看似成功，
**And** 前端显示本人登录状态，不靠 localStorage 里的“已登录”或自填 userId 宣布认证成功。

#### AC-1.2-02 错误凭据和无效输入有明确结果

**Given** 当前未登录且 CSRF 有效，
**When** 提交格式合法但不存在的用户名，或正确用户名配错误密码，
**Then** 均返回 HTTP 401 和相同的“用户名或密码错误”业务提示，不暴露哪个字段命中数据库，且不建立认证状态，
**And** 用户名不符合 D-017 格式、必填项缺失/为空白，或密码 UTF-8 超过 72 字节时返回 HTTP 400；密码值不因登录而改变，普通非空错误密码返回 401，不把密码校验异常变为成功，
**And** 页面显示可理解的失败原因，不返回默认 HTML 登录页、302 跳转或 SQL/堆栈详情。

#### AC-1.2-03 刷新页面以服务端身份恢复状态

**Given** 用户已经登录，
**When** 刷新页面或重新进入前端应用，
**Then** 前端通过 `/api/auth/me` 确认当前身份，当前会话有效则显示本人信息，
**And** 未登录、失效 Cookie 或另一个匿名客户端请求该接口时返回 HTTP 401 JSON，不从浏览器历史或本地缓存恢复已失效权限，
**And** 身份响应不包含密码、密码编码、其他用户资料或可由前端自行授予的全局组织者/管理员权限；当前身份、登录及退出响应设置 `Cache-Control: no-store`。

#### AC-1.2-04 登录和退出均保留 CSRF 保护

**Given** 页面使用同源 `/api` 及服务端会话，
**When** 提交登录或退出请求，
**Then** 缺少/伪造 CSRF 令牌的写请求返回 HTTP 403 JSON，不建立登录或执行退出，
**And** 登录成功或退出后重新通过 `/api/auth/csrf` 获取当前令牌，之后合法的写流程仍可继续，
**And** 使用旧令牌配新的当前会话写入时被拒绝，不能通过关闭 CSRF、改用 GET 执行退出或放开任意来源来规避联调问题。

#### AC-1.2-05 退出使旧会话失效

**Given** 用户持有有效登录 Cookie 和当前 CSRF 令牌，
**When** 提交 `POST /api/auth/logout`，
**Then** 返回 HTTP 200 JSON，服务端注销会话与认证上下文，客户端清除登录态并提示已退出，
**And** 保存并重用退出前 Cookie 请求 `/api/auth/me` 仍为 HTTP 401；不能只删除浏览器中的显示标记，
**And** 旧 Cookie 对测试作用域受保护写路径的请求被拒绝（按实际触发条件为 401/403），其处理器未执行；另以有效匿名 CSRF 请求验证身份校验本身返回 401，
**And** 该受保护处理器只存在测试代码，不随生产应用交付，不以创建未来活动功能来证明本故事完成。

#### AC-1.2-06 过期与正常重启后可重新登录

**Given** 账号已持久化且用户曾登录，
**When** 会话按测试配置过期，或在当前内存会话方案下正常重启后端，
**Then** 旧会话不再被识别为本人，前端收到 401 后清理失效登录显示并提示重新登录，
**And** 原账号和密码编码不变，重新获取 CSRF 后可以用原凭据再次登录，
**And** 不把业务数据持久化误解为必须永久保存登录会话，也不新增“记住我”或自动续登功能。生产会话时长在运行配置中明确，测试使用可控短时长，不伪造实测结果。

#### AC-1.2-07 登录退出不泄露凭据或损坏账号

**Given** 测试了正确登录、失败登录、CSRF 失败、退出及过期路径，
**When** 核对请求处理结果、日志、Cookie 和数据库，
**Then** 响应不含密码或密码编码，日志不含原密码、会话标识或 CSRF 令牌，身份数据不被缓存为可继续授权的依据，
**And** 会话 Cookie 继续满足 HttpOnly、SameSite=Lax，HTTPS 时 Secure；前端不保存可供脚本读取的会话令牌，
**And** 登录、退出和失败请求不修改原用户名、昵称或密码编码，不为本故事创建活动、报名、候补或通知业务表。

#### AC-1.2-08 独立验证并保留证据

**Given** Story 1.1 已实施，本故事可以只使用账号数据运行，
**When** 执行真实账号/数据库、Spring Security 过滤器和会话链路的集成验证，并从浏览器操作页面，
**Then** 保存登录成功/失败、跨请求身份恢复、匿名拒绝、CSRF 更新、旧 Cookie 拒绝、过期/重启再登录的实际结果，
**And** 不能仅依赖手工伪造“已认证用户”的测试注解代替登录/退出链路；受保护测试处理器在交付物中不存在，
**And** 注册功能回归通过，没有依赖尚未创建的 Story 1.3 或后续史诗；本故事不代表未来活动资源权限已全部验证。

#### 已确认的接口及实施约定

| 接口 | 已确认约定 |
|---|---|
| GET /api/auth/csrf | 沿用 1.1 的令牌获取流程；登录与退出后重新获取 |
| POST /api/auth/login | 表单编码的 username/password，带 CSRF Header；成功 200、错误凭据 401、字段错误 400、CSRF 错误 403；均为 JSON |
| GET /api/auth/me | 从服务端会话返回本人 ID/用户名/昵称；有效 200，未登录或失效 401；不能由请求 userId 决定本人 |
| POST /api/auth/logout | 合法 CSRF 请求成功时返回 200 JSON并注销当前会话；不以 GET 执行退出 |

本故事不为“已退出后再次点击退出”强加新的业务承诺：前端以服务端身份和有效 CSRF 状态恢复界面，不将旧令牌拒绝误报成仍在登录。精确字段、错误码、Cookie 配置和测试路径须在实施前纳入单一接口契约，环境供应与运行验证仍待完成，不因规范获批直接标记 ready-for-dev。

框架依据已核对 [会话持久与身份恢复](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)、[退出处理](https://docs.spring.io/spring-security/reference/servlet/authentication/logout.html)、[CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。若自定义认证入口，必须正确保存认证上下文，不能只设置当前线程；本项目要求的 JSON 成功/失败响应也需要明确配置，不能把框架默认页面或跳转当作最终接口。

**边界：**本故事只交付登录、当前身份与退出；不包含找回密码、修改资料、第三方登录、多端会话控制、活动管理或报名。以上 AC 为已批准规范，不是已经执行的测试结果。

### Story 1.3: 保存和修改仅本人可见的活动草稿

As a 准备组织活动的已登录用户，
I want 保存、查看并继续修改自己的活动草稿，
So that 尚未准备完整的内容不会丢失，也不会提前公开给其他同学。

本故事规范已于 2026-11-27 获用户批准（D-019），当前尚未实施或测试。实施前置为已经实施的 Story 1.1/1.2，不依赖发布、公开列表或报名故事；当前获批的是规范，不表示已有实现或测试结果。

**Acceptance Criteria:**

#### AC-1.3-01 已登录用户创建自己的草稿

**Given** 任意普通注册用户已登录并取得有效 CSRF 令牌，
**When** 新建并保存活动草稿，
**Then** 返回 HTTP 201、字符串活动 ID、DRAFT 状态和当前配置版本，发起者取当前会话用户，
**And** 不要求额外的组织者资格或管理员审批；请求不能指定其他 owner，也不能通过夹带 status 将草稿发布，
**And** 新草稿不会创建参加申请、成功名单、候补或通知。

#### AC-1.3-02 不完整草稿可保存并继续编辑

**Given** 用户有自己的草稿，部分字段尚未填写，
**When** 保存、重新进入本人草稿列表并打开该草稿，
**Then** 已填且合法的内容可完整恢复，未填字段明确为未设置，而不是被静默补成默认值，
**And** 全部内容尚未填写时也可暂存，列表显示“未命名草稿”作为展示占位；占位不是实际活动标题，
**And** 报名模式和退出策略分别选择，可以暂不选择；不把先到先得默认解释为自由退出，
**And** 用户能修改本人草稿并再次保存，界面明确显示“草稿/未发布”；保存不等于发布。

#### AC-1.3-03 已填字段非法时拒绝整次保存

**Given** 草稿当前有一份已经保存的内容，
**When** 提交超出下表长度的文本、0/负数/非整数容量、非法模式/策略或无法解析的时间，
**Then** 返回 HTTP 400 和字段错误，旧内容和版本不变，不出现部分字段已更新，
**And** 页面保留本次输入供修正，不显示保存成功；直接请求接口也受到相同校验，
**And** 标题和地点支持中文，说明按纯文本保存和显示；输入的 HTML/脚本不执行，不引入富文本或图片上传。

#### AC-1.3-04 草稿时间按已填组合校验

**Given** 用户正在填写时间，
**When** 保存包含两个或以上相关时间的草稿，
**Then** 已同时填写的报名开始/截止满足开始＜截止，已同时填写的截止/活动开始满足截止≤活动开始，可选结束与开始同时填写时满足开始＜结束；不满足则整次拒绝，
**And** 缺少相关时间时可暂存，不能仅因不完整就报发布必填错误，
**And** 页面输入和展示使用北京时间，接口按统一 UTC 时点往返，刷新后表示同一时刻，
**And** DRAFT 从未开放报名，暂填过去的时间不会生成不可逆的“报名已截止”事实，也不把它认定为活动已经开始而锁死编辑；已发布后的时限与改期规则留给相应故事。

#### AC-1.3-05 草稿仅本人可见、可改

**Given** 用户 A 和 B 各有草稿，另有未登录客户端，
**When** 通过列表、详情或编辑请求直接访问这些草稿，包括猜测 ID 或伪造 owner，
**Then** A 只能列出、读取和修改 A 的草稿，B 同理；对他人的草稿返回 HTTP 404，不泄露字段内容，
**And** 有效匿名 CSRF 下的写请求和匿名读取返回 401；缺少/伪造 CSRF 的写请求按过滤器返回 403，不改变数据，
**And** 本故事不提供公开草稿入口、不允许转移 owner；提交 owner/status 等不可写字段返回 400，记录已不为 DRAFT 时修改返回 409，均不改变数据。

#### AC-1.3-06 重试不重复创建，旧页面不覆盖新内容

**Given** 草稿写请求携带幂等键，编辑还携带读取时的 expectedConfigVersion，
**When** 重试同一次请求，或两个页面用旧版本同时保存，
**Then** 同键同载荷重放原命令结果，不新增第二份草稿或再次提升版本；同键不同载荷返回 409，
**And** 新的有效编辑成功后版本提升，另一个旧版本编辑返回 409 并提示重新读取，不静默覆盖；已提交成功请求的重放先按回执处理，
**And** 不以活动标题唯一来阻止重复，两次有意新建使用不同键，可以有同名草稿；不同用户不能读取彼此回执。

#### AC-1.3-07 失效会话及基础设施失败不伪装成功

**Given** 用户已编辑内容，但会话已失效，或保存遇到数据库错误/锁超时，
**When** 发起保存，
**Then** 按实际原因返回 401/403 或明确的服务端失败结果，未提交的变更全部回滚，
**And** 前端提示重新登录、修正或重试，不先显示保存成功，也不把未保存表单误认为数据库已更新，
**And** 锁等待/并发路径仍按统一活动命令与共享事务约定处理，失败不能留下半份内容或孤立成功回执。

#### AC-1.3-08 刷新和正常重启保留草稿

**Given** 不完整或完整的草稿已成功保存，
**When** 刷新页面，或正常重启后重新登录并进入本人草稿列表，
**Then** 草稿 ID、归属、DRAFT 状态、字段及配置版本保持一致，未填仍为未设置，
**And** 不自动发布、不清空为演示初始数据，不生成额外副本。

#### AC-1.3-09 独立交付并验证最小结构

**Given** 身份功能已实施，本故事尚无后续发布/报名能力，
**When** 由真实页面和 MySQL 验证上述 AC，
**Then** 新增业务结构仅为当前所需的 activities 与必要的 command_receipts，不预建报名、候补、退出或通知表，
**And** 保存合法/不完整草稿、非法输入回滚、时间边界、跨用户拒绝、重复/版本冲突和重启恢复的真实证据；登录/退出及注册回归通过，
**And** 所有当前草稿路由均需登录并核对 owner，发布及公开列表未实现时不以假接口证明“未公开”；后续公开查询必须回归过滤 DRAFT，
**And** 不增加删除/复制草稿、图片、标签、组织管理、报名自定义表单或报名功能；当前只有规划规范，没有测试结果。

#### 已确认的草稿字段与保存约定

所有字段在 DRAFT 中均可暂不填写；空白标题/地点视作未填，非空时去首尾空白。说明的有效正文保留换行。长度按 Unicode 码点计，前后端一致；不以 Java UTF-16 长度和浏览器不同计数方式各自实现。

| 字段 | 已确认的保存约束 |
|---|---|
| 标题 | 至多 100 个字符，支持中文；未填时仅在界面显示“未命名草稿” |
| 活动说明 | 至多 5000 个字符，纯文本；全为空白视作未填 |
| 地点 | 至多 200 个字符，支持中文 |
| 容量 | 未填或正整数，不另加业务人数上限；超出接口整数可表示范围时明确拒绝，不能溢出 |
| 报名开始、报名截止、活动开始 | 可分别未填；已填相关时间按 AC-1.3-04 校验；页面北京时间 |
| 活动结束 | 可选；与开始都填写时须晚于开始，不改变“活动开始前”这一既定处理截止 |
| 报名模式 | 未设置、先到先得、发起者审核三种字段情况；不虚构第三种业务模式 |
| 退出策略 | 未设置、自由退出、退出须审核三种字段情况；独立于报名模式 |

这些约定解决草稿编辑所需字段，不提前批准未来的发布、已发布活动改期到过去或实际参与规则。发布所需必填项在 Story 1.4 明确；本故事不执行发布。

| 接口 | 约定用途 |
|---|---|
| POST /api/activities/drafts | 创建本人 DRAFT；允许不完整内容，写请求携带幂等键，成功 201 |
| GET /api/me/activity-drafts | 只列本人 DRAFT，返回 ID、标题/展示占位依据、修改时间及配置版本；无草稿时为空列表 |
| GET /api/activities/{activityId}/draft | 本人草稿详情；他人/不可见记录 404 |
| PUT /api/activities/{activityId}/draft | 仅修改仍为 DRAFT 的本人记录，带幂等键及 expectedConfigVersion；成功 200，非法 400，版本/状态/幂等键冲突 409 |

精确字段名、未设置值的 JSON 表示及版本类型在实施前统一进接口契约，不能由前后端分别猜测。登录/CSRF 沿用已批准的 Story 1.2，ID 用字符串；记录归属取会话。保留最小可审查迁移和日志，不记录密码、会话令牌或私密草稿全文。

### Story 1.4: 发布活动并选择初始报名模式和退出策略

As a 已经准备好活动草稿的发起者，
I want 完善必填信息，选择报名模式和退出策略并发布，
So that 同学可以通过公开详情了解活动及参与条件。

本故事规范已于 2026-11-27 获用户批准（D-020），尚未实施或测试。实施前置为 Story 1.1–1.3，规范获批不表示已实现。为避免反向依赖 Story 1.5，本故事同时交付最小公开详情；公开列表及人数展示由后续对应故事增量承接，不把本故事等同于 FR-04/FR-05 全部场景已完成。

**Acceptance Criteria:**

#### AC-1.4-01 本人完整草稿可以发布

**Given** 当前用户已登录，有有效 CSRF 令牌，草稿属于本人且仍为 DRAFT，字段完整合法、版本未过期，
**When** 带幂等键与 expectedConfigVersion 提交发布，
**Then** 返回 HTTP 200、原活动字符串 ID、PUBLISHED 状态、配置版本和发布时间，活动不会另建第二份记录，
**And** 发起者、已保存字段、报名模式和退出策略按服务端当前草稿生效；版本提升，保存不可由客户端伪造的发布时间，
**And** 页面显示真实发布结果和可打开的公开详情链接，不依赖未来列表或报名接口来证明发布成功。

#### AC-1.4-02 不完整草稿不能被发布

**Given** 草稿缺少下表任一发布必填项，或包含非法字段/关系，
**When** 请求发布，
**Then** 返回 HTTP 400 及明确的缺失/非法字段，仍为原 DRAFT，旧内容和版本不变，
**And** “未命名草稿”的界面占位不能充当实际标题；模式、退出策略不得自动补成默认选项，
**And** 未保存的表单更改必须先保存成功再发布，页面不能无提示地把旧版本内容发布，
**And** 不完整草稿仍可按 Story 1.3 修改，发布失败不锁死或删除草稿。

#### AC-1.4-03 发布时复核当前时间

**Given** 时间字段满足报名开始＜报名截止≤活动开始，结束未填或晚于开始，
**When** 在活动锁内检查发布条件及最终写入边界，
**Then** 报名截止必须晚于实际校验时点；已到截止或活动已开始的草稿返回 HTTP 409，不发布，
**And** 允许报名开始早于或等于当前时点，只要尚未截止；也允许未来才开始报名，
**And** 报名截止等于活动开始仍合法，不人为添加必须存在的“截止后审核窗口”，
**And** 等待锁或处理中跨过截止时重新取时并回滚，不能用页面或请求刚到达时的旧时间放行；DRAFT 发布失败不生成已对外关闭报名的事实。

#### AC-1.4-04 初始两种模式与两种退出策略独立

**Given** 发起者已在草稿中明确选择一种报名模式和一种退出策略，
**When** 分别发布四种组合，
**Then** 先到先得/参加审核与自由退出/退出须审核的四种组合均可保存为已发布设置，并在公开详情清晰展示，
**And** “参加审核”由发起者后续审核报名者，不是发布活动本身要找管理员审批；没有新增组织者资格门槛，
**And** 发布本身不等于发起者报名、不自动创建参加记录，不决定发起者以后能否手动报名自己的活动。

#### AC-1.4-05 发布权限与草稿入口保持隔离

**Given** 另一用户或匿名客户端知道草稿 ID，或请求试图伪造 owner/status，
**When** 读取私有草稿或发布，
**Then** 他人草稿按既定约定 404，匿名有效 CSRF 请求为 401，缺少/伪造 CSRF 的写请求为 403，数据不变，
**And** 发布仅接受约定的版本等控制字段，不通过发布接口顺带覆盖 owner、标题或模式，
**And** 发布后不再出现在本人草稿列表，原草稿修改接口不能继续改它；已发布编辑、切换和取消仍由 Epic 3 承接。

#### AC-1.4-06 重试和并发不能重复发布或覆盖内容

**Given** 同一草稿可能被两个页面保存/发布或出现网络重试，
**When** 执行这些命令，
**Then** 同键同载荷的成功回执先于新命令的状态/时限检查重放，不重复发布时间、版本或状态变化；同键不同载荷为 409，
**And** 不同键再次发布已发布活动，或旧版本发布，返回 409，不创建副本、不覆盖新内容，
**And** 保存先成功时旧版本发布失败；发布先成功时后续草稿保存失败；所有变更遵守同一活动锁和事务。

#### AC-1.4-07 发布后可访问最小公开详情

**Given** 活动已成功发布，或另一个 ID 仍为 DRAFT/不存在，
**When** 未登录或已登录用户通过公开详情链接访问，
**Then** 已发布活动返回 HTTP 200，展示标题、说明、地点、发起者展示名、时间、容量、报名模式和退出条件，
**And** DRAFT 和不存在的 ID 均为 404，不向匿名用户回退到私有草稿内容，
**And** 不暴露账号秘密、完整名单、私密申请或回执，不执行文本中的 HTML/脚本，
**And** 本故事不提供假报名按钮、模拟成功人数或虚构剩余名额；活动列表和后续人数/报名能力由对应故事真实接入。

#### AC-1.4-08 失败原子性与重启恢复

**Given** 发布过程中可能发生数据库错误/锁超时，或成功发布后正常重启，

**Then** 失败时状态、版本、发布时间和成功回执不部分生效，不出现页面说成功而记录仍是草稿，
**And** 已成功发布的状态、设置、时间与原 ID 在重启后保留；重新登录后也不能借原草稿接口再次发布/修改，
**And** 初次发布不要求填写“活动变更说明”，也不生成不存在的原名单通知；后续修改须说明和通知的已确认规则不因此取消。

#### AC-1.4-09 独立交付并回归原流程

**Given** 前三条故事已实施，本故事没有未来的公开列表、报名、模式迁移或通知功能，
**When** 用真实页面、会话和 MySQL 验证发布，
**Then** 保存完整/缺项、已截止边界、四种设置组合、跨用户拒绝、版本/重试/并发、公开详情隐私及重启恢复的实际证据，
**And** 只增量扩展当前需要的 activities 字段及既有回执，不预建报名、候补、退出、变更通知业务表，
**And** 注册、登录/退出、草稿保存回归通过；没有因新增公开接口而放开草稿或整段 `/api` 的权限，

### Story 1.5: 公开浏览已发布活动列表与详情

As a 想了解班级或社团活动的同学，
I want 无需登录即可查看已发布活动列表，打开详情了解时间、名额及参与条件，
So that 可以判断哪些活动值得进一步参加。

本故事规范已于 2026-11-27 获用户批准（D-021），尚未实施或测试。实施前置为 Story 1.1–1.4。规范扩展最小公开详情并建立发现列表，不依赖未来报名写接口；取消的创建、原因/历史和沉底仍由 Epic 3 连同取消流程接入，规则未删除。获批不表示已实现或测试，也不声称已完整交付 FR-05 的取消场景。

**Acceptance Criteria:**

#### AC-1.5-01 未登录也能发现已发布活动

**Given** 存在已发布活动、本人/他人的草稿，以及尚未登录的访问者，
**When** 打开活动列表，
**Then** 列表可正常读取而不跳到登录页，只返回当前已交付范围内的 PUBLISHED 活动，DRAFT 永不出现在公开列表，
**And** 每项显示标题、发起者展示名、地点、时间、模式、容量与名额信息，并可打开已有公开详情，
**And** 默认按发布时间从新到旧，相同发布时间按数据库活动 ID 数值稳定倒序，由服务端统一排序，前端不按字符串重新排序；已截止或已开始的活动不被默认隐藏，
**And** 本故事不新增搜索、筛选或分页；若以后采用分页，必须保持完整结果排序后再分页的已确认规则。

#### AC-1.5-02 详情完整表达参与条件

**Given** 活动已发布，或请求的 ID 仍为草稿/不存在，
**When** 匿名或已登录用户打开详情，
**Then** 已发布记录返回 HTTP 200，展示标题、纯文本说明、地点、发起者展示名、报名起止、活动开始、可选结束、当前模式和独立退出策略，
**And** 未填结束时间明确表示未设置，不猜测结束时刻；四种模式/退出组合均按实际值显示，
**And** 草稿或不存在记录均为 404，不回退到私有草稿，也不泄露其标题或拥有者。

#### AC-1.5-03 剩余名额取真实成功记录

**Given** 数据库中存在已发布活动及有效测试数据，包括 CONFIRMED、PENDING、WAITLISTED、REJECTED、WITHDRAWN、EXITED 等记录，
**When** 读取列表或详情，
**Then** 已占名额等于该活动 CONFIRMED 数量，剩余名额等于容量减该数量；待审、候补及非成功历史不减位，
**And** 容量与人数来自同一数据库快照，不能拼接两个时点或用前端自行计数；没有记录时由真实查询得到 0，不硬编码演示人数，
**And** 为这个只读计数建立当前确实需要的最小报名记录及归属结构；后续写故事复用并增量扩展，不要求先实现提交/审核/退出，
**And** 退出待审仍属于 CONFIRMED 的既定语义不变；真实退出申请与计数的联动在对应退出故事验证，不把本次夹具读查询测试说成退出流程已经运行。

#### AC-1.5-04 时间状态取服务端时点

**Given** 时间有效的已发布活动，服务端返回本次读取采用的时间依据，
**When** 读取或刷新列表/详情，
**Then** 按下表显示当前阶段，不以访问者电脑时间判断资格，
**And** 恰好到报名开始时进入报名中，恰好到截止时不再显示仍在接收新申请，恰好到活动开始时显示已开始；截止等于开始时不制造不存在的中间窗口，
**And** 若已有持久化的报名关闭事实且未开始，仍显示报名已截止，即使后来改期后的日期尚在未来；本故事只读取，不修改关闭事实，
**And** 页面按北京时间展示接口中的 UTC 时点，不能因为浏览器时区不同改变业务阶段。

#### AC-1.5-05 满额提示区分报名模式

**Given** 活动在报名时间窗口内，剩余名额为 0，
**When** 分别查看先到先得与审核模式，
**Then** 先到先得明确显示名额已满，审核模式明确说明“名额已满，仍可提交待审核申请；待审核不代表报名成功”，
**And** 未开始、已截止或已开始等时间限制不因审核模式或剩余名额大于 0 而被忽略，
**And** 本故事仅表达阶段、人数与规则，不新增报名写入口或返回假报名成功；也不替尚未确认的发起者自报名规则给出本人一定可报名的判断。

#### AC-1.5-06 公开读取不扩大私密权限

**Given** 系统已有受保护的身份、私有草稿路由和公开活动路由，
**When** 匿名用户读取公开活动并尝试读取私有草稿/本人身份或调用写接口，
**Then** 只对精确的公开 GET 路径开放访问，不将整段 `/api` 或活动写接口开放，
**And** 公开响应不含完整名单、退出理由、私密申请、密码、会话标识或命令回执；当前身份/私有数据仍按前述故事拒绝匿名访问，
**And** 文本按纯文本展示，不执行脚本；无效/不可见 ID 有明确 400/404 JSON 结果，公开正常请求不会返回默认登录 HTML 或 302。

#### AC-1.5-07 空列表、失败和刷新有真实反馈

**Given** 没有已发布活动、接口失败或请求正在加载，
**When** 用户打开列表或详情，
**Then** 分别显示加载、暂无已发布活动、读取失败或不存在的明确状态，不用示例活动伪装真实结果，
**And** 刷新重新读取数据库结果，列表/详情使用 `Cache-Control: no-store`，不把旧缓存人数或时间状态当作最新资格，
**And** Cookie 已过期不阻断匿名可用的公开浏览，当前身份失败不会把整个公开页面强制导向登录，
**And** 读取不创建申请、不占名额、不更新配置版本、通知已读或报名关闭事实。

#### AC-1.5-08 正常重启保留活动与展示依据

**Given** 活动已发布且相关记录已存入真实 MySQL，
**When** 正常重启再读取，
**Then** 活动 ID、字段、发布时间与顺序保持一致，名额按原有记录重新计算，
**And** 时间阶段可随真实时间推进，不能把“阶段变化”误判为数据丢失，也不能为恢复旧显示回写时间，
**And** 草稿仍私有，注册、登录/退出、草稿和发布流程不因新增读取功能失效。

#### AC-1.5-09 独立验证与阶段边界

**Given** 未来的报名、审核、退出、模式变更和取消写流程尚未实施，
**When** 用真实 MySQL 测试夹具核对公开读模型，并以浏览器完成发现/详情路径，
**Then** 保存列表顺序、同刻稳定排序、隐私、计数、时间边界、两种模式满额提示、空/失败状态及重启读取的实际证据，
**And** 只创建当前读模型所需的最小 participation_slots / registration_attempts 字段与约束，以及确需的活动读取字段；不预建退出请求、变更或通知表，
**And** 夹具只用于测试，不提供对外造数据后门或模拟报名界面，不把夹具记录称为真实使用者报名，
**And** 不把读查询验证写成未来写流程、最后名额并发或完整取消流程已完成，当前不直接标记 ready-for-dev。

#### 已确认的阶段显示约定

以下仅定义展示，不改变已确认的报名、审核、退出和补录截止规则。优先按已结束/已开始判断，再判断不可逆关闭事实与报名起止。

| 条件 | 显示 |
|---|---|
| 填写了结束且服务端时间已到结束 | 活动已结束 |
| 已到活动开始、但不满足上项 | 活动已开始 |
| 未开始，已有关闭事实或已到报名截止 | 报名已截止 |
| 未开始、未关闭，未到报名开始 | 报名未开始 |
| 未开始且报名开始≤当前时间＜截止，没有关闭事实 | 报名中；满额另按模式提示 |

未填结束时间时，开始后只显示“已开始”，不自动假设持续时长。本次已确认默认保留已截止/已开始/已结束的已发布活动，不增加按阶段隐藏的规则。

#### 读取、表结构与接口约定

- `GET /api/activities`：本故事的公开列表，空结果为 200 和空列表；默认发布时间倒序、ID 倒序，不做新增筛选或分页。
- `GET /api/activities/{activityId}`：扩展 Story 1.4 的公开详情，补齐真实名额和阶段；不另建第二套公开详情协议。

- Epic 3 开放整场取消时，按已确认规则把 CANCELLED 纳入完整列表并全局沉底，补齐原因/历史详情与通知；当前不生成取消入口，不把本次完成当作 FR-05 取消场景已验收。

As a 已登录、希望参加活动的同学，
I want 在报名期内报名先到先得活动，并查看本人是否成功入名单，
So that 能根据服务端的真实结果安排参与，而不是把点击按钮当作获得名额。

本故事于 2026-11-27 经用户回复“通过”批准（D-023），尚未实施或测试。实施以前五条故事为基础；活动保持既有设置，不依赖未来参加审核、退出、模式切换、候补或通知代码。规范获批不等于实现或测试完成，不直接标为 ready-for-dev。

**已确认 S-1（D-023）：允许发起者手动报名自己的活动，遵守相同时间、容量和重复规则，占一个正常名额；发布不自动报名。**审核模式下也须提交并审核自己的参加申请，不因发起者身份自动通过；实际审核场景由后续故事承接。PRD 已同步关闭自报名保留项，名单字段等其他保留项不因此关闭。

**Acceptance Criteria:**

#### AC-2.1-01 有名额时真实报名成功

**Given** 用户已登录并取得有效 CSRF 令牌，目标为已发布的先到先得活动，处于报名窗口且未持久关闭报名，本人没有当前有效申请，并有可分配名额，
**When** 在详情页提交报名，服务端在统一活动事务中受理，
**Then** 返回 HTTP 201、报名尝试字符串 ID、CONFIRMED 状态及版本；创建或使用本人的唯一参与槽位，并将当前指针指向此次尝试，
**And** 服务端保存原始受理时间和活动内唯一受理序号，不接收客户端伪造的申请时间、状态、用户或队列位置，
**And** 已占人数增加恰好一人，公开详情按真实记录计算剩余名额；报名不提升活动配置版本，不自动创建退出请求或变更通知。

#### AC-2.1-02 时间与模式条件在实际受理时检查

**Given** 页面可能已过时，活动可能尚未开放、已截止、已开始、未发布，或当前采用参加审核模式，
**When** 提交新的先到先得报名命令，
**Then** 报名开始时允许、截止时及以后禁止，即报名开始≤服务端时间＜截止，且不能绕过已保存的报名关闭事实，
**And** 已发布但时间/模式不符返回 409 和具体业务原因；未发布或不存在按公开不可见约定返回 404，不能偷读草稿，
**And** 先取得活动行锁，再以独立 SQL 读取数据库 UTC 时间；分配名额前和最终写入前重新核对适用边界，跨截止时整条命令回滚，不使用浏览器时间或等待锁前的旧时间放行。

#### AC-2.1-03 满额失败与最后名额竞争

**Given** 活动已满，或多个不同用户竞争最后一个名额，
**When** 并发提交报名，
**Then** 最多一个用户新增成功记录，其余返回 409 CAPACITY_FULL；不出现负剩余人数、超过容量或失败者的有效报名，
**And** 满额失败不自动加入候补、不产生待审申请，也不保存“报名成功”的历史；页面显示真实失败并刷新名额，
**And** 按统一活动根行锁、同一 Spring JDBC READ_COMMITTED 事务计数和写入，CONFIRMED 记录数为名额真值，不引入第二份可写人数。

#### AC-2.1-04 同人并发和网络重试不重复占位

**Given** 用户双击、两个页面同时操作，或提交成功后响应丢失，
**When** 以相同或不同幂等键再次提交，
**Then** 同一用户同一活动最多一条当前有效申请，已有成功记录时不同键报名返回 409 ALREADY_PARTICIPATING，并提示读取本人当前状态，
**And** 身份/目标权限校验后，同键同载荷成功回执先于新的状态/时限检查重放原结果；即使后来已截止，也只重放而不重新占位；同键不同目标/载荷返回 409，
**And** 回执与报名同事务保存；跨活动复用键的唯一冲突须回滚后核对原回执，不造成两次报名。重放后页面重新读取当前状态，不能将历史成功回执当作永久有效资格。

#### AC-2.1-05 本人状态可独立查询与刷新

**Given** 用户可能尚未报名，或已通过本故事成功报名，
**When** 详情加载、刷新、报名返回后或网络结果不确定时读取本人在该活动的当前参与状态，
**Then** 未报名返回 HTTP 200 和明确的无当前申请结果；已成功返回本人 CONFIRMED、尝试 ID、版本、受理时间及活动退出策略，
**And** 页面展示“报名成功”，刷新或重新登录后仍可查，不能仅依赖本地变量或 toast 维持结果，
**And** 本故事只提供当前活动的本人最小状态入口；跨活动“我的报名”、完整尝试历史和后续状态增量由对应故事承接，不等待它们才能确认本次结果。

#### AC-2.1-06 身份隔离与发起者自报名

**Given** 匿名用户、另一用户或活动发起者尝试报名/读取个人状态，
**When** 服务端处理请求，
**Then** 身份仅取会话，不允许用 userId/actorId 代别人报名；非法身份/状态控制字段返回 400，其他人的尝试、名单和秘密不出现在响应中，
**And** 有效 CSRF 的匿名写请求及匿名个人查询为 401，缺少/伪造 CSRF 的写请求为 403，公开活动读取仍无需登录；私人响应使用 no-store，
**And** 按已确认 S-1（D-023），发起者手动报名自己的活动时也须有名额且处于报名期，成功后占一个名额，无自动报名或额外名额；本项仍待实际测试，规范获批不等于软件验收通过。

#### AC-2.1-07 基础设施失败不留下部分结果

**Given** 事务写入或回执保存出错、发生死锁/锁超时，或客户端没有收到明确响应，
**When** 回滚并重新查询或使用原幂等键重试，
**Then** 失败不留下部分尝试、当前指针、序号更新或成功回执，已确认的旧数据不受损；基础设施失败为可重试 503，不泄露 SQL 及连接信息，
**And** 页面明确区分“失败”和“结果暂未确认”，先查询本人状态再按原键重试，不凭超时宣称已成功或另开第二次占位，
**And** 重试重新取锁、取时并核对资格，不能因先前请求曾进入系统而绕过截止。

#### AC-2.1-08 正常重启保留报名事实

**Given** 多名用户已取得成功报名响应，
**When** 刷新页面或正常停止并重启应用，必要时重新登录，
**Then** 原活动、参与槽位、尝试 ID、状态、原始时间/序号和成功回执保持，当前成功人数与公开名额一致，
**And** 不以演示数据重建、清空业务表或持久化登录会话来替代业务数据持久性，
**And** 活动即使已经截止或开始，成功记录仍可查，不能把时间推进误作丢失或自动退出。

#### AC-2.1-09 独立交付与实际证据

**Given** 仅 Epic 1 和本故事已实施，尚无后续审批、退出、候补、模式修改及通知能力，
**When** 用浏览器和真实 MySQL 验证报名及本人结果，
**Then** 保存合法报名、满额、边界、最后一席竞争、同人竞争、同/异键重试、权限、回滚及正常重启的实际证据，并回归前五条故事，
**And** 基于 Story 1.5 已有最小关系做所需增量迁移，只补当前指针、受理时间/序号、唯一约束及回执等确需字段；不预建退出、通知或全部未来状态处理流程，
**And** 并发测试使用独立测试库，实际请求数、轮次和环境须记录；A-6 的 50 请求/20 轮仍待确定，不把建议预算或 SQL 夹具写成实测，
**And** 不开放虚假的审核/退出入口，也不宣称完整 FR-15、未来队列公平性或其他未实施流程已验收。

### Story 2.2: 提交参加审核申请并查看待审状态

As a 已登录、希望参加需审核活动的同学，
I want 在报名期内提交参加申请并明确看到待审核状态，
So that 知道申请已被系统接收，同时不会误以为已经取得活动名额。

本故事于 2026-11-27 经用户回复“通过”批准（D-024），尚未实施或测试。实施以前六条已批准规范为前置，扩展同一报名与本人状态入口；提交申请及读取结果不依赖未来发起者审核页面才能工作。活动设置在本阶段保持不变；不提前实现候补、模式修改、退出和通知。

**Acceptance Criteria:**

#### AC-2.2-01 审核模式提交后为待审核

**Given** 用户已登录并取得有效 CSRF 令牌，已发布活动采用参加审核模式，处于报名期、未持久关闭，本人没有当前有效申请，
**When** 在详情页明确点击“提交参加申请”并携带幂等键提交，
**Then** 返回 HTTP 201、本人新尝试的字符串 ID、版本、服务端受理时间及 PENDING 状态，页面明确显示“待审核，尚未报名成功”，
**And** 建立或使用本人的唯一参与槽位，指向该申请；沿用活动锁下的原始受理时间与唯一序号，不接受客户端指定身份、申请状态或排队时间，
**And** 申请数增加，CONFIRMED 人数和剩余名额不变；不提升活动配置版本，不创建退出申请或活动变更通知。

#### AC-2.2-02 满额仍可申请且不自动通过

**Given** 审核活动已满，或已有多名待审用户而容量只有一个，
**When** 其他用户在报名期内提交有效申请，或随后重新读取待审结果，
**Then** 满额仍接收为 PENDING，不以 CAPACITY_FULL 拒绝该审核申请，也不把 PENDING 总数限制为活动容量，
**And** 待审不占位、不按提交先后自动获得名额；即使存在空位，提交或查询本身都不得转为 CONFIRMED，
**And** 审核模式下以后释放空位也不自动通过，实际退出释放与此规则的交错验证由相应后续故事承接；本故事不声称尚未实现的退出流程已测。

#### AC-2.2-03 新申请时间边界与现存申请分开处理

**Given** 新申请可能遇到尚未开放、已截止或已开始，而此前已受理的申请仍为 PENDING，
**When** 提交新的申请或读取已有申请，
**Then** 新申请仅在报名开始≤数据库当前时间＜截止且未持久关闭时受理，开始时允许、截止时禁止；不因满额仍可申请而绕过时限，
**And** 取得活动锁后用独立 SQL 取时，最终写入前重新取时复核，等待锁或处理跨截止则整条申请回滚，
**And** 截止前提交的 PENDING 在截止后保留可查，开始前提示“待审核”；到活动开始后仍不自动批准或删除，并派生显示“待审核，处理已截止”，不把派生提示另存成已拒绝或已撤回。

#### AC-2.2-04 同人重复与成功回执重放

**Given** 同一人双击、两页并发，或已成功提交但响应丢失，
**When** 以相同或不同幂等键再次提交，
**Then** 同人同活动最多一条当前有效申请；已有 PENDING 或 CONFIRMED 时不同键提交返回 409 ALREADY_PARTICIPATING，并提示读取本人结果，不刷新原受理时间/序号，
**And** 身份/目标权限检查后，同键同载荷成功回执先于新命令时限及状态检查重放；截止后也仅重放原提交结果，不新建申请；同键不同目标/载荷为 409，
**And** 重放后重新读取当前状态，不能因原回执是 PENDING 就覆盖后来已变化的状态；跨活动复用键的唯一冲突必须整条回滚后校验回执。

#### AC-2.2-05 页面及统一入口区分两种模式

**Given** 详情可能为先到先得或参加审核模式，客户端表单也可能过时，
**When** 用户查看报名操作并提交，
**Then** 先到先得按钮表达直接报名，审核模式按钮表达提交申请，成功提示分别为 CONFIRMED 与 PENDING；本人状态沿用既有查询入口，
**And** 同一报名端点以服务端模式裁决；请求携带期望报名模式只用于校验操作意图，不能覆盖活动模式，意图与当前模式不一致返回 409 并要求刷新，不静默将申请变为直接占位或反向转换，
**And** 本故事在共同契约中为两种分支补齐 expectedEnrollmentMode 控制字段及对应页面，不另建可绕过模式的直接通过接口；Story 2.1 的先到先得命令和回执语义保留，旧页面须明确刷新，
**And** 本人状态返回真实 PENDING、ID、版本和受理时间；无当前申请仍为 200 空状态，私人响应 no-store，不依赖未来跨活动历史页面。

#### AC-2.2-06 权限与已确认的发起者自申请

**Given** 匿名用户、其他用户或活动发起者本人操作参加申请，
**When** 申请或查询本人状态，
**Then** 身份只取会话，不能代别人申请、指定 CONFIRMED 或读取他人的私密记录；非法身份/状态字段为 400，匿名有效 CSRF 写请求和私人查询为 401，伪造/缺少 CSRF 写请求为 403，
**And** 未发布/不存在的活动为 404，已发布但新申请时间、模式意图或业务状态冲突为 409；返回业务原因但不泄露数据库或他人记录，
**And** 按 D-023，发起者可以手动对自己的审核活动申请，但仍先为 PENDING、不占位、不自动通过；其后处理本人申请也须执行同一审核规则，由审核故事承接，
**And** 退出策略 FREE/APPROVAL_REQUIRED 均不改变参加审核规则，不因允许自由退出就直接录入名单。

#### AC-2.2-07 失败回滚与网络结果核对

**Given** 当前指针、尝试、序号或回执保存可能失败，或响应未到达客户端，
**When** 回滚、查询本人状态或按原键重试，
**Then** 事务失败不留下半条申请、孤立当前指针或成功回执，不破坏原有数据；死锁/锁超时返回可重试 503，
**And** 页面不凭点击或超时宣称提交成功；结果未知时查询本人结果，重试沿用原幂等键，不额外生成一次申请，
**And** 重试重新取锁取时，已越截止且没有原成功回执时拒绝，不把最初请求到达时间当作提前取得资格。

#### AC-2.2-08 正常重启保留待审和顺序

**Given** 一些申请已成功受理，包含满额时提交的 PENDING，
**When** 刷新或正常重启后重新登录并查询，
**Then** 申请 ID、状态、当前指针、原始时间/序号及回执保持，待审仍不减名额，
**And** 后续模式切换必须能沿用这些原始排序键，但本故事不提前生成候补或宣称迁移已完成，
**And** 查询只读，不自动审核、清空或重建申请；时间推进后的处理已截止提示按当前时间推导。

#### AC-2.2-09 独立验证并回归先到先得

**Given** 只实施 Epic 1、Story 2.1 及本故事，尚无未来审核、退出或变更功能，
**When** 用真实页面、会话与 MySQL 验证提交及读取，
**Then** 保存普通/满额提交、不占位、同人并发、同/异键重试、时限、模式意图、隐私、自申请、四种设置组合及重启的实际证据，
**And** 只扩展现有尝试的 PENDING 路径、必需约束与既有接口，不提前建退出请求、名单管理、审核写入口或通知表；未来审核能力没有完成并不妨碍本故事独立提交和读取结果，
**And** 回归 Story 2.1 真实直接占位、最后名额竞争、同人唯一与时限规则，不把所有活动统一改成待审核，
**And** 实际测试环境、请求数和结果须记录；当前仅规范获批，没有运行证据，不直接标为 ready-for-dev 或通过软件验收。

#### 已确认的共同契约增量

继续使用 `POST /api/activities/{activityId}/registrations`，首次受理统一为 201、状态由服务端模式决定。D-024 已确认请求体带 `expectedEnrollmentMode`，枚举沿用现有 FIRST_COME_FIRST_SERVED / APPROVAL_REQUIRED，用于拒绝过时操作意图；不是可编辑的业务设置。回执摘要包含该字段，重放优先于新命令模式/时限门槛，重放后再查询当前结果。

`GET /api/activities/{activityId}/my-participation` 增量返回 PENDING；前端同时显示活动参与条件和本人状态。精确 JSON、HTTP/错误码及兼容提示须先进入共同契约，再由两位成员核对；BIGINT 字符串、UTC 时间、北京时间显示、会话/CSRF 和秘密保护沿用既有约定。

### Story 2.3: 发起者查看参加申请和当前成功名单

As a 活动发起者，
I want 查看自己活动的参加申请、待审人数和当前成功名单，
So that 能区分申请与实际参加者，掌握真实名额，为后续审核提供依据。

本故事于 2026-11-27 经用户回复“通过”批准（D-025），尚未实施或测试。前置为已经批准的七条规范；实施按其顺序完成，本故事利用现有 PENDING/CONFIRMED 记录即可独立读取，不等待未来参加/退出审核、重报或模式迁移才能工作。

**已确认 A-5（D-025）：当前成功名单的用户可见字段只包括用户名、昵称、报名状态。**申请记录另显示原提交时间以辅助审阅；接口为后续操作提供尝试 ID、版本等必要技术标识，但不因此显示账号秘密、手机号、学号、邮箱或退出理由。本次不增加导出或批量审核功能。PRD 的 A-5 已按 D-025 关闭，其他保留项不因本次批准关闭。

**Acceptance Criteria:**

#### AC-2.3-01 本人活动可进入申请与名单视图

**Given** 当前用户已登录，目标活动由其发起并已经发布，
**When** 从本人活动管理入口打开参加管理页，
**Then** 页面可查看“申请记录”和“当前成功名单”，显示目标活动标题、模式、容量、待审核人数和成功人数，数据来自本人活动的真实记录，
**And** 在既有活动详情中为本人提供参加管理入口，服务端仍独立核对归属，不依赖未来“我发起的全部活动”列表才能打开，
**And** 没有申请时返回 HTTP 200、空集合和零人数，显示明确空状态，不使用虚构示例填充，
**And** 本故事只提供读取，不放置尚未实现的通过、拒绝、退出审核、取消或导出按钮来伪装流程完整。

#### AC-2.3-02 申请记录与当前状态不混淆

**Given** 活动存在此前通过 Story 2.1/2.2 受理的申请，未来也可能通过对应故事产生终态历史，
**When** 发起者读取该活动的申请记录，
**Then** 每条真实尝试独立列出用户名、昵称、该次报名状态及原提交时间；当前有效尝试与历史尝试明确区分，同一人的多次尝试不覆盖或合并成一次，
**And** 当前 PENDING 明确为“待审核、尚未报名成功”，CONFIRMED 为成功；未来拒绝、撤回、退出状态须随其真实写故事增量接入，不把未实施状态造入生产数据，
**And** 接口提供该次尝试的字符串 ID、版本和当前标记，为后续审核定位该次记录，不能只用用户 ID 代表任意一轮报名；读取不产生审核结果。

#### AC-2.3-03 成功名单只包含真实占位者

**Given** 同一活动可能有成功、待审及非成功历史记录，
**When** 查看当前成功名单，
**Then** 名单只包含当前有效且状态为 CONFIRMED 的报名，每人至多一行；PENDING、未来候补及已拒绝/撤回/退出记录不进入成功名单，
**And** 按已确认 A-5（D-025），用户可见字段仅用户名、昵称和报名状态，不展示密码、编码值、会话、私密账号资料或退出理由，
**And** 已确认的“退出待审仍成功占位”规则保留；实际退出请求尚未实施，本故事不创建退出表或声称该联动已验证，后续退出故事须使其继续在名单中并补充准确状态提示。

#### AC-2.3-04 人数与名额来自同一一致快照

**Given** 读取期间可能有其他用户提交申请或报名，
**When** 服务端构建一次参加管理响应，
**Then** 成功人数等于该快照中的成功名单行数和 CONFIRMED 数，待审核人数仅计当前 PENDING；容量、已占与剩余满足剩余＝容量−成功人数，
**And** 申请历史总条数不能作为成功人数或待审人数，不把重报历史重复计入当前人数，
**And** 以同一数据库一致快照读取容量、汇总与对应集合，不能拼接不同查询时点造成同一次响应人数与名单矛盾；不引入独立可写人数计数器，
**And** 公开活动与管理页若在不同请求时点读取可以因真实并发而不同，不能用缓存旧数据宣称同时一致；刷新后按各自真实快照呈现。

#### AC-2.3-05 资源权限在服务端检查

**Given** 匿名访问者、普通参与者、另一活动发起者，或本活动发起者本人直接请求接口，
**When** 读取目标活动的申请、成功名单和管理汇总，
**Then** 匿名请求为 401；其他登录用户读取公开已发布活动的管理数据为 403，不能因知道活动 ID、参加过活动或能管理别的活动而越权，
**And** 不存在或对请求者不可见的草稿为 404；本人草稿不接收报名，管理读取返回 409 ACTIVITY_NOT_PUBLISHED，而不是伪装成可报名活动，
**And** 身份及发起者归属只取会话和数据库，不接受 ownerId/actorId 绕过检查；拒绝响应不夹带他人名单或申请，
**And** 精确公开活动 GET 接口继续只返回公共字段，不能为方便复用而将名单、申请和私人汇总并入公开详情。

#### AC-2.3-06 原始顺序和时间边界不触发写入

**Given** 活动处于报名中、已截止或已开始阶段，且记录仍保留，
**When** 查看申请与名单，
**Then** 按 D-025，申请记录与成功名单均按原提交时间升序、同刻按活动内受理序号数值升序稳定排列，由服务端排序，
**And** 该显示顺序不是审核模式的自动批准或强制先进先出规则；不因排在前面就生成成功资格，
**And** 截止或开始后仍允许发起者读取；开始后待审保留并提示“处理已截止”，不自动批准、拒绝、删除或重排原申请时间，
**And** 时间取服务端，显示沿用北京时间；首次版本不增加筛选或分页，未来如增加分页必须先全局稳定排序。

#### AC-2.3-07 只读、隐私和失败状态真实

**Given** 请求成功、网络失败、身份过期或数据库查询失败，
**When** 页面加载或刷新参加管理数据，
**Then** 显示对应加载、空、拒绝或失败状态，失败不显示为“无人报名”，也不将上一活动的名单留作当前活动结果，
**And** 私人接口及页面数据响应使用 no-store，退出登录或切换用户时清除先前私人视图；不在日志记录账号秘密或退出理由，昵称等内容按纯文本呈现，
**And** 读取路径保持只读，不修改活动配置、尝试版本、当前指针、受理时间、名额或回执，不以查询触发自动通过或补录，
**And** 基础设施失败按既有 503 约定返回，不泄露 SQL；重试仅重读，不要求为 GET 新建幂等回执。

#### AC-2.3-08 刷新与正常重启保留真实视图

**Given** 用户已通过前置故事保存报名和待审申请，
**When** 刷新或正常重启后重新登录查看，
**Then** 原有申请 ID、时间/序号、当前状态及其对应名单和人数保持，页面不回到演示数据或依赖浏览器本地缓存，
**And** 查询本身不新增或丢失数据，阶段提示随真实时间推进，不能将提示变化误作申请状态被改写，
**And** 注册、草稿、发布、公共浏览、两种报名与本人状态读取仍可用，未为管理视图扩大公开权限。

#### AC-2.3-09 独立验证与后续增量边界

**Given** 前七条规范与本故事按顺序实施，而未来审批、退出、重报、迁移和取消尚未实现，
**When** 使用真实页面及 MySQL 验证管理读取，
**Then** 保存空视图、两个模式下已有记录、归属隔离、最小字段、稳定排序、并发读取快照、截止/开始后读取、错误提示及正常重启的实际证据，
**And** 尚无业务写入口的终态/多次尝试可用仅限独立测试库的 SQL 夹具验证查询，但必须标明夹具，不能冒充真实审核、撤回、退出或重报已经工作，
**And** 只增加当前查询确需的索引和投影，不预建审核流水、退出请求、变更或通知表，不用未来故事代码作为前置，
**And** 当前仅规范获批，A-5 和显示顺序已由 D-025 确认，运行结果尚不存在，不直接标记 ready-for-dev 或课程软件验收通过。

成功名单显示用户名、昵称和报名状态；申请记录另显示原提交时间。尝试 ID、版本、当前标记、排序键等接口元数据只为准确关联与后续操作使用，不放大用户可见账号资料范围。所有 BIGINT 标识/序号用十进制字符串，前端不得字符串重排；响应和 HTTP 约定沿用既有契约。

### Story 2.4: 发起者通过或拒绝参加申请

As a 活动发起者，
I want 在活动开始前通过或拒绝自己活动的待审核参加申请，
So that 能按活动需要确定参加者，同时保证名额正确且申请人可查询真实结果。

本故事于 2026-11-27 经用户回复“通过”批准（D-026），尚未实施或测试。前置为八条已批准规范；本故事在既有管理页接入真实审核操作，并扩展本人结果查询，不依赖未来撤回、退出或完整历史页面。活动设置在本阶段保持不变，迁移/取消增量仍在 Epic 3。

D-026 已确认拒绝参加的理由选填及以下输入边界：**拒绝理由为纯文本，去首尾空白后最多 500 个 Unicode 码点；未填或全空白按未提供处理。**只有发起者和该申请人可查看理由，不因本故事新增对外通知渠道。

**Acceptance Criteria:**

#### AC-2.4-01 有名额时通过当前待审申请

**Given** 发起者已登录且持有有效 CSRF，活动已发布、当前为参加审核模式且未开始，目标是本活动当前有效 PENDING 尝试，版本匹配，尚有名额，
**When** 从管理页对明确的尝试 ID 提交通过，携带 expectedVersion 和幂等键，
**Then** 返回 HTTP 200，目标变为 CONFIRMED 且版本增加，当前槽位继续指向该次尝试，仅增加一个成功名额，
**And** 保存服务端审核人和审核时点，保留原提交时间/受理序号，不将每次审核当作活动配置变更，不改变其他申请，
**And** 申请人可在既有本人状态入口看到报名成功，发起者刷新名单/汇总得到真实结果，公开名额按同一 CONFIRMED 真值计算。

#### AC-2.4-02 拒绝只结束目标申请且理由选填

**Given** 同样满足归属、模式、未开始、当前 PENDING 和版本条件，活动也可能已满，
**When** 发起者对该次尝试提交拒绝及可选理由，
**Then** 返回 HTTP 200，尝试变为 REJECTED、版本增加，清除该用户在本活动的当前指针，保留尝试和服务端审核信息，不删除历史，
**And** 拒绝不需要空余名额，不改变 CONFIRMED 人数或产生释放名额动作，不顺带通过其他申请，
**And** 按 D-026 已确认规则，理由去首尾空白后最多 500 个 Unicode 码点，空白可不提供，超长或类型非法返回 400 且整体不变；按纯文本保存/展示，
**And** 不允许用拒绝参加的入口移除已成功者；已成功者的退出只由对应退出故事处理。

#### AC-2.4-03 审核期限与报名截止分开

**Given** 待审申请已在允许的报名期内受理，当前可能在报名截止前、截止后或活动开始边界，
**When** 提交通过或拒绝，
**Then** 报名截止不阻止审核既有申请，允许处理到活动开始前；服务端时间等于或晚于开始时返回 409 REVIEW_CLOSED，待审保持可查，不自动拒绝或批准，
**And** 同一活动行锁内以独立 SQL 在锁后取数据库 UTC 时间，并在分配名额前及最终写入前重新检查适用开始边界；等待锁或处理中跨开始时整个命令回滚，
**And** 当前模式不是参加审核时禁止人工通过/拒绝，不按旧页面模式处理，不给先到先得活动提供人工插队入口；未来模式切换/取消必须在对应 Epic 3 增量接入同一校验。

#### AC-2.4-04 最后名额及同一申请并发

**Given** 只剩一席而发起者同时通过不同申请，或两个页面对同一申请做通过/拒绝，
**When** 并发执行审核命令，
**Then** 不同申请最多新增一名成功者，容量不足为 409 CAPACITY_FULL、该申请仍 PENDING，版本和审核信息不被部分更新，
**And** 同一申请只能有一个符合前置状态/版本的结果生效，后续不同键命令为 409 STATE_CONFLICT 并提示刷新，不出现同时拒绝和成功，
**And** 沿用统一活动根行锁及同一 Spring JDBC READ_COMMITTED 事务，计数和指针/状态/回执同事务，不维护第二份可写成功人数，
**And** 审核模式不要求按列表先后通过，也不因旧申请排在前面就自动占位；发起者仍可选择任何有效待审申请，容量和期限检查不变。

#### AC-2.4-05 旧请求及重试不能重复改变结果

**Given** 用户双击、成功响应丢失、旧页面仍持有旧版本，未来也可能已有新一轮申请，
**When** 使用相同/不同幂等键重试审核，
**Then** 身份/目标权限校验后，同键同目标/载荷成功回执先于新命令的模式/状态/时限门槛重放，不重复占位或再次拒绝；同键不同载荷/目标返回 409，
**And** 无原成功回执的新命令必须检查当前指针仍指向此尝试、状态 PENDING 和 expectedVersion；否则为 409，不能按用户 ID 将旧审核套到另一轮申请，
**And** 重放注明原结果/版本并刷新真实状态，不用历史成功回执覆盖已变化的页面；跨活动复用键唯一冲突整条回滚后核对，
**And** 未来撤回/重报与旧审核的真实交错由相应故事验证；当前可用独立测试库夹具验证旧指针拒绝，不能冒充未来流程已经实现。

#### AC-2.4-06 申请人可读取通过和拒绝结果

**Given** 申请已获批或被拒绝，拒绝时当前指针已清除，
**When** 申请人在原活动详情刷新或重新登录，
**Then** 既有本人结果入口显示成功或最近一次拒绝结果；拒绝者不能因“无当前有效申请”被显示成从未申请，提供的理由仅本人可见，
**And** 返回当前有效尝试，并在没有当前尝试时提供最新尝试的 ID、终态、审核时间和可选理由，明确区分当前与历史；最新按原提交时间和活动受理序号确定，
**And** 此最小结果读取随本故事交付，不等待 Story 2.9 的跨活动完整历史；未来重报后旧拒绝不得遮盖新一轮当前状态，
**And** 不新增站内审核结果通知、短信等源需求未要求的功能，页面读取不得触发状态变化。

#### AC-2.4-07 所有权与理由隐私

**Given** 匿名用户、普通参与者、另一活动发起者或本活动发起者直接请求审核，
**When** 服务端校验活动归属及目标尝试，
**Then** 有效 CSRF 的匿名写请求为 401，伪造/缺少 CSRF 的写请求为 403；只有本活动发起者可审核，其他登录用户对公开已发布活动审核为 403，
**And** 活动不存在/不可见为 404；核实活动管理权后，尝试不存在或不属于该活动为 404，不泄露另一活动的申请；不接受客户端伪造审核人、目标用户、状态或时间，
**And** 按 D-023，发起者本人提交的待审申请也可由其以发起者身份按同一审核操作处理，通过仍受容量、版本和时限约束，不自动批准，
**And** 拒绝理由仅该申请人及发起者可读，公开详情、成功名单和日志不带理由；私人响应 no-store，切换用户清除旧私人视图。

#### AC-2.4-08 失败原子性与正常重启

**Given** 状态、审核信息、指针或回执写入失败，或命令成功后正常重启，
**When** 分别核对回滚和重新读取，
**Then** 失败不留下部分审核结果、扣位、清指针或成功回执；死锁/锁超时等为可重试 503，不泄露 SQL，客户端查询真实状态后沿原键重试，
**And** 成功后的审核结果、审核人/时点、可选拒绝理由、尝试版本、指针及回执正常重启后保留，原提交时间/序号不变，
**And** 页面明确区分失败与结果未知，不凭点击显示审核成功；重试无原成功回执时重新取锁/取时/检查资格，不能绕过开始边界。

#### AC-2.4-09 独立交付及真实证据

**Given** 前八条规范与本故事按顺序实施，未来撤回、退出、重报、模式迁移和取消尚未实施，
**When** 用真实页面、会话及 MySQL 验证审核和本人结果，
**Then** 保存通过/拒绝、可选理由、满额拒绝仍可执行、最后一席、同一申请冲突、重复回执、截止后审核/开始边界、越权、本人自申请审核、结果读取与重启的实际证据，
**And** 只扩展当前 attempts 的审核字段、版本及 REJECTED 路径和既有回执，不预建退出/通知表或独立审批流水系统，
**And** 回归先到先得和待审提交、管理视图与本人状态，既定名单字段及原提交时间排序不因审核改变；审核通过的后申请不会被按审核时间重新排队，
**And** 并发验证记录实际请求数/轮次/环境，A-6 预算未确认前不当作实测；当前仅规范获批，没有运行结果，不直接标记 ready-for-dev 或软件验收通过。

### Story 2.5: 本人撤回尚未入名单的参加申请

As a 尚未进入活动成功名单的申请人，
I want 在活动开始前自行撤回参加申请，
So that 不再等待审核，也不会在放弃参加后仍被录入名单。

本故事于 2026-11-27 经用户回复“通过”批准（D-027），尚未实施或测试。前置为九条已批准规范；本故事交付现有审核模式 PENDING 的撤回，以及与已存在的通过/拒绝操作的真实竞争。WAITLISTED 由 Epic 3 模式迁移产生时，再同时接入候补撤回，既定规则不删除。当前不依赖未来退出或重报页面，不新增撤回理由或审批门槛。

**Acceptance Criteria:**

#### AC-2.5-01 活动开始前本人可直接撤回待审

**Given** 申请人已登录并有有效 CSRF，活动已发布且未开始，本人当前有效尝试为 PENDING、指针和版本匹配，
**When** 从活动详情的本人结果区提交撤回，带目标尝试 ID、expectedVersion 及幂等键，
**Then** 返回 HTTP 200，尝试变为 WITHDRAWN、版本增加，清除该用户本活动的当前指针，保留原尝试、原提交时间/受理序号并记录服务端撤回时点，
**And** 不需发起者批准或填写理由，不受活动自由退出/限制退出策略影响；未入名单的撤回与成功后的退出是不同操作，
**And** 原申请不再可通过或拒绝，也不被未来迁移/补录复活；CONFIRMED 人数和剩余名额不变，不产生释放名额、自动通过他人或通知。

#### AC-2.5-02 截止后仍可撤回，开始时停止

**Given** 申请在报名期内已受理，而当前可能已经报名截止，
**When** 本人提交新撤回命令，
**Then** 只要当前时间早于活动开始，就允许撤回有效待审，不要求仍在报名窗口；报名截止不影响此资格，
**And** 服务端时间等于或晚于开始时返回 409 WITHDRAWAL_CLOSED，申请仍保留，不能自动撤回或伪装为拒绝，
**And** 在统一活动行锁内用独立 SQL 锁后取数据库 UTC 时间，最终写入前再次核对开始边界，等待锁或处理跨开始时整条撤回回滚，不依赖浏览器时间，
**And** 活动不存在或不可见为 404；不对草稿生成参加申请，未来整场取消必须随 Epic 3 同时关闭撤回入口。

#### AC-2.5-03 撤回与审核并发只生效一个结果

**Given** 发起者正在通过或拒绝同一 PENDING 申请，本人同时撤回，
**When** 两个操作竞争统一活动锁和尝试版本，
**Then** 撤回先成功时，后续通过/拒绝返回 409 STATE_CONFLICT，申请保持 WITHDRAWN、不入名单，
**And** 通过先成功时，撤回返回 409 STATE_CONFLICT，页面刷新显示已报名成功、该申请不可撤回；不能借撤回入口绕过成功者的退出策略，不能自动转换为直接退出，
**And** 拒绝先成功时，撤回返回 409 并显示实际拒绝结果，不改写为本人主动撤回，
**And** 同一 Spring JDBC READ_COMMITTED 事务内检查当前指针、状态和 expectedVersion 再变更，不产生已撤回又成功的矛盾记录，失败不破坏已经提交的另一操作。

#### AC-2.5-04 幂等重试不改写历史或新尝试

**Given** 双击、响应丢失、旧页面或未来已经存在新一轮尝试，
**When** 相同/不同幂等键提交撤回，
**Then** 身份/目标权限检查后，同键同载荷成功回执先于新的状态/时限门槛重放；开始后也只重放原结果，不二次撤回；同键不同载荷/目标为 409，
**And** 已撤回的尝试用新键重试、版本过时或当前指针已变化时返回 409，不能改变旧终态或清除另一轮申请的指针，
**And** 历史回执注明原结果/版本，页面随后重新读本人当前结果；跨活动复用键的唯一冲突整条回滚后核对回执，不产生第二次业务变化，
**And** 旧请求与真实重报的联动在 Story 2.9 增量验证，本故事可用独立测试库夹具验证指针变化保护，不冒充已实现重报。

#### AC-2.5-05 仅本人可撤回，发起者无代撤回权

**Given** 匿名用户、另一申请人、活动发起者或该申请人本人直接请求，
**When** 校验撤回目标与当前会话，
**Then** 有效 CSRF 的匿名写请求为 401，伪造/缺少 CSRF 的写请求为 403；身份只取会话，不接受 userId/actorId、状态或处理时间覆盖，非法字段为 400，
**And** 目标尝试不存在、属于他人或不属于路径活动时为 404，不泄露他人私密申请；发起者可以拒绝申请，但不能通过本人的撤回接口代他人撤回，
**And** 发起者自己申请的活动也允许其以申请人身份撤回，遵守同一状态/时间/版本规则；不因管理身份绕过资格，
**And** 私人返回保持 no-store，不向公开详情增加申请人身份、撤回记录或拒绝理由。

#### AC-2.5-06 撤回结果在本人及管理视图可查

**Given** 本人申请已撤回，当前指针已清除，
**When** 刷新本人结果区或发起者的参加管理视图，
**Then** 本人最小结果查询保留“无当前有效申请，但最近尝试已撤回”的明确信息，不显示成从未申请；发起者的历史申请中显示该次 WITHDRAWN，待审人数减少且不进入成功名单，
**And** 成功人数、剩余名额不因撤回变化，名单仍只显示已确认字段，按原提交时间/受理序号排序；查询不触发审核、补录或状态变更，
**And** 冲突时展示服务端真实结果，不能只隐藏按钮或使用本地状态伪装撤回成功；当前已经成功、已拒绝或无有效申请时不展示可用的待审撤回操作，
**And** 完整跨活动历史和重报入口在 2.9 提供，不等待它才能看到本次撤回结果；真实个人退出在后续故事提供，不用无效按钮代替。

#### AC-2.5-07 失败原子性与正常重启

**Given** 状态、当前指针或回执保存失败，或撤回成功后正常重启，
**When** 分别核对回滚与重新登录读取，
**Then** 失败不产生半次撤回、孤立指针或成功回执，原数据保持；锁超时/死锁等为可重试 503，不泄露 SQL，
**And** 响应未知时先读取本人结果并按原键重试，不凭超时认定成功；无原成功回执的新执行须重新取锁、取时和校验，不能绕过开始边界，
**And** 正常重启后 WITHDRAWN、版本、撤回时点、原始排序键、已清除指针及回执保留，不恢复为待审或清空历史，
**And** 回归两种报名、审核、本人状态与管理读取，不把记录持久性等同于永久登录会话。

#### AC-2.5-08 独立验证与候补增量边界

**Given** 前九条规范与本故事按顺序实施，尚无模式迁移候补、退出或重报写流程，
**When** 用真实页面、会话及 MySQL 验证撤回，
**Then** 保存截止后撤回、两种退出策略下的待审撤回、开始边界、与通过/拒绝竞争、同/异键重试、旧指针/版本、他人拒绝访问、结果读取、回滚与正常重启的实际证据，
**And** 仅补当前 WITHDRAWN 路径及必要撤回时点/索引、当前指针和既有回执，不预建退出请求、候补或通知表，不要求未来故事代码，
**And** Epic 3 在开放真实 WAITLISTED 的同一增量中接入候补撤回与补录竞争；已确认的“未入名单且活动未开始可撤回”覆盖候补，不能因当前仅有 PENDING 实现而删除候补规则，
**And** 并发记录实际请求数、轮次及环境，不把 A-6 建议预算或测试夹具写成已测结果；当前仅规范获批，未实现或运行，不直接标为 ready-for-dev 或软件验收通过。

#### 已确认的接口增量

`POST /api/activities/{activityId}/registrations/{attemptId}/withdraw`：会话本人撤回，携带 expectedVersion 与 Idempotency-Key，成功为 200 和 WITHDRAWN/版本。不接受撤回理由、目标用户或期望新状态；精确 JSON 和错误码纳入共同契约，两位成员核对后实施。

### Story 2.6: 已报名成功者按自由退出策略退出

As a 已报名成功但临时无法参加的同学，
I want 在活动允许自由退出且尚未开始时自行退出，
So that 明确结束本次参加并释放名额，供其他符合规则的人使用。

本故事于 2026-11-27 经用户回复“通过”批准（D-028），尚未实施或测试。前置为十条已批准规范，当前活动设置保持不变；先到先得成功与审核通过成功均已可由前置故事产生，本故事对两者使用同一自由退出规则。不依赖未来退出申请、重报、模式迁移或通知代码，不新增退出理由或发起者审批。

**Acceptance Criteria:**

#### AC-2.6-01 自由退出结束本次成功参加

**Given** 参与者已登录并有有效 CSRF，活动已发布且未开始，当前退出策略为 FREE，本人当前有效尝试为 CONFIRMED，指针及版本匹配，
**When** 从活动详情本人结果区提交直接退出，携带目标尝试 ID、expectedVersion 和幂等键，
**Then** 返回 HTTP 200，目标尝试变为 EXITED、版本增加，清除本人本活动的当前指针，保留原记录和原提交时间/受理序号，记录服务端退出时点，
**And** 不需理由或发起者批准，不新增退出申请；该次尝试不再占名额、不进入当前成功名单，不能被旧审核重新改回成功，
**And** 不修改活动容量或配置版本，不物理删除历史，不将用户主动退出记作活动取消或撤回未入名单申请。

#### AC-2.6-02 按实际策略及开始边界校验

**Given** 用户已成功入名单，报名可能已经截止，页面显示的活动条件也可能过时，
**When** 提交新的直接退出命令，
**Then** 报名截止后仍允许在开始前自由退出；服务端时间等于或晚于活动开始时返回 409 EXIT_CLOSED，不改变成功资格，
**And** 当前策略要求审核时返回 409 EXIT_REVIEW_REQUIRED，不直接释放名额，不静默代用户生成退出申请；该申请流程在后续故事交付，
**And** PENDING 或无当前成功尝试不能用本接口退出，返回 409 状态冲突；待审者仍用 Story 2.5 的撤回，不绕过两类操作的边界，
**And** 同一活动行锁内，用独立 SQL 锁后取数据库 UTC 时间，最终写入前复核开始边界；等待锁或处理中跨开始时整条命令回滚，不以浏览器时间放行。

#### AC-2.6-03 名额只随真实退出释放

**Given** 活动为任一种报名模式，已有多个成功者和可能的待审申请，
**When** 一名成功者完成自由退出，
**Then** 该事务 CONFIRMED 数减少恰好一人，剩余名额增加恰好一个；成功名单与容量/人数读取沿用一致快照，不能只改前端数字或维护另一份可写计数，
**And** 先到先得模式仅在报名仍开放时允许其他人按既有规则新报名，退出不延长截止；截止后释放空位也不收新申请，
**And** 审核模式下待审不因空位自动通过，仍须由发起者在开始前按既有审核入口处理，
**And** 当前固定设置阶段没有迁移候补；未来先到先得旧候补优先补录的 FR-23 增量必须随 Epic 3 接入此释放事务，不能把本阶段空位行为当成完整公平队列已验收。

#### AC-2.6-04 重复退出和旧请求不重复释放

**Given** 用户双击、成功响应丢失、旧页面或未来已有新的报名尝试，
**When** 使用同/异幂等键提交退出，
**Then** 身份/目标权限检查后，同键同载荷成功回执先于新命令的策略/状态/时限门槛重放，开始后也只重放，不再次退出或释放；同键不同目标/载荷为 409，
**And** 已退出尝试以新键提交、旧版本或当前指针已变时返回 409 STATE_CONFLICT，不清除另一轮申请，不重新释放名额，
**And** 历史回执注明原结果/版本，页面再读取当前真实状态；跨活动复用键唯一冲突整条回滚后核对回执，
**And** 与真实重报的联动在 Story 2.9 增量验证，本故事可用独立测试库夹具验证旧指针保护，不假称已经实现重报。

#### AC-2.6-05 退出与报名竞争仍满足容量不变量

**Given** 活动已满，一人退出的同时其他用户报名，或两页同时退出同一成功尝试，
**When** 这些命令竞争同一活动根行锁，
**Then** 所有计数、当前指针、状态和回执在统一 Spring JDBC READ_COMMITTED 事务内检查及写入，任何成功响应后都不超容量、不出现负剩余名额，
**And** 报名先检查满额时可以失败；退出提交后新的有效报名才可使用释放的空位，不承诺所有并发报名都成功，不自动重试成另一次报名，
**And** 同一成功尝试只退出一次；另一不同键命令冲突，不能产生两个可用名额，
**And** 等待锁后重新取时，跨报名截止的新报名拒绝、跨活动开始的新退出拒绝，两种命令不能互相借用较宽的时间窗口。

#### AC-2.6-06 仅本人有直接退出权限

**Given** 匿名用户、另一参与者、活动发起者或该成功者本人直接请求退出，
**When** 服务端核对目标尝试与当前会话，
**Then** 有效 CSRF 的匿名写请求为 401，伪造/缺少 CSRF 的写请求为 403，身份仅取会话，不接受目标用户、状态或处理时间覆盖，非法字段为 400，
**And** 目标不存在、属于他人或不属于路径活动时为 404；发起者无权通过此接口代别人退出，不能把管理活动权当作强制移出名单权，
**And** 发起者本人参加自己的活动时可作为参与者退出，仍遵守 FREE、CONFIRMED、版本及开始边界，没有额外豁免，
**And** 私人响应保持 no-store，不向公开活动返回参与者身份或退出历史；当前没有新增退出理由字段。

#### AC-2.6-07 本人和发起者看到真实退出结果

**Given** 自由退出已成功并清除当前指针，
**When** 本人刷新活动详情或发起者读取参加管理视图，
**Then** 本人最小结果区显示“无当前有效参加，最近尝试已退出”，不显示成从未报名或仍成功；发起者历史中保留 EXITED，但当前成功名单移除该人，
**And** 名单、待审/成功人数和公共名额按既定规则读取，申请记录按原提交时间/受理序号排序，不用退出时间重排旧申请，
**And** 页面根据当前状态及策略提供真实操作：待审可撤回，成功且 FREE 可在开始前直接退出；不能把退出待审或旧成功回执显示成已退出，
**And** 状态/时限冲突时刷新服务端结果，失败或响应未知不先移除本人/名单；结果读取随本故事交付，不等待未来跨活动历史或重报页面。

#### AC-2.6-08 失败原子性与正常重启

**Given** 状态、退出时点、指针或回执写入失败，或成功退出后正常重启，
**When** 分别检查回滚和重新登录读取，
**Then** 失败不产生部分退出、错误释放或成功回执，已提交数据不受损；死锁/锁超时等返回可重试 503，不泄露 SQL，
**And** 响应未知时先查询本人状态再按原键重试，无成功回执的新执行须重新取锁、取时及检查资格，不绕过开始边界，
**And** 正常重启保留 EXITED、版本、退出时点、原始排序键、已清除指针和成功回执，人数/名单不恢复旧资格，
**And** 不清空业务数据或依赖浏览器缓存恢复结果，持久性不要求永久保存会话。

#### AC-2.6-09 独立验证与后续增量

**Given** 前十条规范及本故事按顺序实施，尚无退出审核、重报、模式迁移或取消功能，
**When** 使用真实页面、会话及 MySQL 验证直接退出，
**Then** 保存两种报名来源下 FREE 退出、受限策略拒绝直退、待审不可直退、截止后/开始边界、释放后新报名或手动通过、双重退出、旧指针、身份隔离、结果查询、回滚与正常重启的实际证据，
**And** 只增加当前 EXITED 路径和所需退出时点/约束，不预建退出请求、队列或通知表；实际并发请求数、轮次及环境如实记录，不把 A-6 预算或夹具写成运行结果，
**And** Epic 3 开放策略变更和候补迁移时，须同时将此直接退出接入原待审退出请求的关闭/指针清理和旧候补同步补录；不能先开放变更后再等待未来补保护，当前不依赖其代码，
**And** 回归两种报名、参加审核、撤回和管理读取，当前仅规范获批，没有运行证据，不直接标记 ready-for-dev 或软件验收通过。

#### 已确认的接口增量

`POST /api/activities/{activityId}/registrations/{attemptId}/exit`：会话本人直接退出，携带 expectedVersion 与 Idempotency-Key，成功 200、EXITED/版本；不接受退出理由、目标用户或期望新状态。受限退出请求使用后续独立流程，不能由此接口自动生成。

继续扩展本人最小结果入口及发起者管理读取，提供当前成功资格与最近 EXITED 的准确区分；保持既有 BIGINT 字符串、UTC 时间、北京时间显示、JSON/HTTP 和 CSRF 规则。精确字段与错误码先进入共同契约，由两位成员核对后实施。

### Story 2.7: 受限退出时提交理由并撤回待审退出申请

As a 已报名成功但无法参加、且活动要求审核退出的同学，
I want 说明理由申请退出，也能在改变主意时撤回尚未处理的退出申请，
So that 发起者能了解情况，而申请期间我的参加资格和名额不会被提前取消。

本故事于 2026-11-27 经用户回复“通过”批准（D-029），尚未实施或测试。前置为十一条已批准规范；在固定活动设置下提供真实提交、撤回及私人读取，不依赖未来审核按钮才能提交/撤回。退出通过或拒绝由 Story 2.8 实现，策略变更、候补补录和取消仍随 Epic 3 接入。

D-029 已确认退出理由必填及仅本人/发起者可见，并确认以下输入边界：**退出理由使用纯文本，去首尾空白后为 1–500 个 Unicode 码点，空白、超长或类型非法均拒绝。**这不是沿用参加申请的“拒绝理由选填”，也不新增证明材料或附件要求。

**Acceptance Criteria:**

#### AC-2.7-01 成功者提交受限退出申请

**Given** 用户已登录且有有效 CSRF，活动已发布、未开始，当前退出策略为 APPROVAL_REQUIRED，本人当前尝试为 CONFIRMED 且版本匹配，没有待审退出请求，
**When** 提交理由、报名尝试 ID、expectedVersion 及幂等键，
**Then** 返回 HTTP 201、新退出请求字符串 ID、PENDING、版本和服务端提交时间，将其关联到本次报名尝试并设为唯一待审退出指针，报名尝试版本相应增加，
**And** 报名状态仍为 CONFIRMED，仍在成功名单且占原名额，原报名提交时间/受理序号不变；不清除当前参加指针，不释放名额或补录他人，
**And** 申请人与发起者能读取真实请求，页面明确显示“报名成功，退出待审核”，不能只显示含糊的“待审核”或“已退出”。

#### AC-2.7-02 必填理由与非法请求整体拒绝

**Given** 退出申请包含未填、全空白、非文本或过长理由，或客户端试图指定目标用户、状态或处理时间，
**When** 服务端校验提交，
**Then** 按 D-029 已确认规则，理由去首尾空白后须为 1–500 个 Unicode 码点；非法为 HTTP 400，明确指出输入问题，申请、指针、版本和回执不部分生效，
**And** 合法理由按纯文本保存/展示，不执行 HTML/脚本；不将理由混写为参加审核拒绝理由或活动变更说明，
**And** 请求仅使用会话本人及指定报名尝试；理由不能在普通日志、公共详情、成功名单或其他人的本人接口中出现。

#### AC-2.7-03 时间及资格以实际服务端状态为准

**Given** 报名可能已截止，活动可能开始，或当前报名/退出策略已与页面不同，
**When** 提交新的退出申请，
**Then** 报名截止后仍可在活动开始前提交；开始时及以后为 409 EXIT_CLOSED，不自动退出或自动通过，历史仍可查，
**And** 无当前成功尝试、尝试版本过时或已有待审退出请求为 409；当前允许自由退出时不创建受限退出申请，提示按实际策略刷新操作，
**And** 两种报名来源的成功者采用同一规则；尚未进入名单的 PENDING 不可申请退出，仍按 Story 2.5 撤回参加申请，
**And** 统一活动根行锁内独立 SQL 锁后取数据库 UTC 时间，最终写入前复核开始边界；等待锁或处理跨开始则整条命令回滚，不使用浏览器旧时间。

#### AC-2.7-04 本人撤回待审退出请求不退出活动

**Given** 活动未开始，本人仍是该活动当前成功者，目标退出请求为 PENDING，报名尝试的待审退出指针仍指向它，请求版本匹配，
**When** 本人按明确退出请求 ID、expectedVersion 和幂等键撤回退出申请，
**Then** 返回 HTTP 200，请求变为 WITHDRAWN、请求版本增加，清除待审退出指针并提升报名尝试版本，保留请求、理由、原提交时间和服务端撤回时点，
**And** 参加状态仍为 CONFIRMED、仍占位并在名单中，不释放名额；页面显示报名成功以及最近退出申请已撤回，不把它当作撤回参加申请，
**And** 撤回资格不要求仍在报名期，也不要求当前退出策略仍受限；到开始时关闭，未来策略变更后仍须由当前状态和指针裁决，不能使旧请求再次释放名额，
**And** 不提供直接修改待审理由的另一入口；如需更正可先撤回，再按当时资格提交新的退出请求，旧请求终态和理由保留。

#### AC-2.7-05 重复、并发及旧请求保护

**Given** 同人双击、两页并发提交/撤回、成功响应丢失，或同次报名后来出现新的退出请求，
**When** 使用同/异幂等键操作，
**Then** 同一报名尝试最多一个有效待审退出请求；不同键重复提交为 409 EXIT_REQUEST_PENDING，不新增并行请求或覆盖理由，
**And** 身份/目标权限检查后，同键同载荷成功回执先于新的状态/策略/时间门槛重放；同键不同载荷/目标为 409，跨活动复用键唯一冲突整条回滚后核对，
**And** 撤回只处理指定的 PENDING 请求及匹配指针/版本；旧终态、新请求、旧报名尝试或过时版本返回 409，不清除新的待审指针，不改写历史，
**And** 撤回后若仍具备提交资格，可产生新请求 ID、版本及提交时间；原幂等键只重放旧结果，页面随后读取当前请求，不将旧回执套到新请求，
**And** 与发起者通过/拒绝退出的真实竞争由 Story 2.8 接入，当前不冒充审核写流程已完成。

#### AC-2.7-06 本人操作与理由访问隔离

**Given** 匿名用户、另一参与者、活动发起者或该报名者本人请求操作/读取，
**When** 服务端核对会话、活动、报名尝试及退出请求归属，
**Then** 有效 CSRF 的匿名写请求及匿名私人读取为 401，缺少/伪造 CSRF 的写请求为 403；目标不存在、属于他人或不属于路径活动/尝试为 404，
**And** 只有申请人本人可提交和撤回自己的退出请求；发起者只能查看本活动的退出理由，不能代参与者申请或撤回；其本人参加时按相同参与者资格操作，
**And** 其他登录用户读取公开已发布活动的退出管理视图为 403，不因能管理别的活动而获权；私人响应 no-store，切换用户清除旧私人视图，
**And** 名单仍仅展示已批准的用户名、昵称和报名状态；理由放在专门的私人退出申请视图，不扩大名单或公共字段范围。

#### AC-2.7-07 本人和发起者可独立查看请求

**Given** 已提交或撤回过退出请求，
**When** 本人读取当前活动参与结果，或发起者从既有管理页查看退出申请，
**Then** 本人可看到当前待审请求及在无待审时最近退出请求的状态、时间、理由，明确它属于哪一次报名，不能误以为已经失去参加资格，
**And** 发起者的私人退出申请视图显示真实请求和理由、关联尝试/请求 ID 及版本；本故事不放置未实现的通过/拒绝按钮，后续审核据该请求定位，
**And** 待审退出仍计入 CONFIRMED 及成功名单，报名成功人数/剩余名额不变，退出待审提示不改变已确认的名单资料范围，
**And** 参加待审核人数仍只统计报名 PENDING，不把退出请求的 PENDING 混入参加待审统计，
**And** 到活动开始后未处理请求保持可查并提示处理已截止，不自动批准、退出或删除；读取为只读，不更新业务状态/版本或创建回执，
**And** 不等待跨活动完整历史才能查看本次请求及撤回结果，不新增退出结果通知、邮件或短信要求。

#### AC-2.7-08 事务失败及正常重启

**Given** 请求记录、待审指针、尝试版本或回执保存失败，或操作成功后正常重启，
**When** 分别核对回滚和重新读取，
**Then** 失败不留下孤立请求、指针或成功回执，不改报名资格和名额；死锁/锁超时等为可重试 503，不泄露 SQL 或私密理由，
**And** 统一活动根锁及同一 Spring JDBC READ_COMMITTED 事务保护请求/尝试/回执，响应未知时先查本人结果并按原键重试，重新执行须复核资格和实际时间，
**And** 正常重启保留请求/报名 ID、状态、理由、原提交/撤回时间、版本、指针和回执，待审不恢复为已退出或清空理由，
**And** 活动阶段提示可随真实时间推进，不能将提示变化误判为请求终态变化或数据丢失。

#### AC-2.7-09 独立验证与最小结构

**Given** 前十一条规范及本故事按顺序实施，尚无后续退出审核、重报、策略变更或取消能力，
**When** 用真实页面、会话及 MySQL 验证提交、读取及撤回，
**Then** 保存两种报名来源下受限退出、必填/空白/超长理由、截止后/开始边界、并发唯一、重复回执、撤回/重提与旧请求、理由权限、名单占位、回滚及正常重启的实际证据，
**And** 此时才创建当前所需 exit_requests、报名尝试的 pending_exit_request_id 及约束/版本增量；只提供 PENDING/WITHDRAWN 路径，不提前实现审批结果、候补或通知表，
**And** 回归自由退出、参加审核、待审撤回及现有读取；释放名额须等待退出获批，不能为给本故事制造成功结果而提前改变 CONFIRMED，
**And** 审核的真实竞争在 2.8、被拒后重提在对应拒绝流程、改策略后旧请求关闭及取消终态在 Epic 3 同时接入；实际环境/请求数/轮次如实记录，不用建议预算替代证据，
**And** 当前仅规范及理由长度获批，没有运行结果，不直接标为 ready-for-dev 或软件验收通过。

#### 已确认的接口增量

| 接口 | 本故事用途 |
|---|---|
| POST /api/activities/{activityId}/registrations/{attemptId}/exit-requests | 本人提交；报名尝试 expectedVersion、reason、Idempotency-Key，首次 201 |
| POST /api/activities/{activityId}/exit-requests/{exitRequestId}/withdraw | 本人撤回；退出请求 expectedVersion、Idempotency-Key，成功 200 |
| GET /api/activities/{activityId}/my-participation | 扩展本人当前/最近退出请求，不改变当前成功参加的语义 |
| GET /api/activities/{activityId}/exit-requests | 仅本活动发起者私人读取退出请求；不合并进入公开详情或公开名单 |

精确字段和错误码先进入共同契约，两位成员核对后实施。提交和撤回是不同对象/版本操作：提交检查报名尝试版本，撤回检查退出请求版本及其当前指针，不能互换。采用既有 BIGINT 字符串、UTC 时间和北京时间展示、会话/CSRF 及回执约定。

理由在当前待审时不直接编辑，撤回后可重新提交仍是按当前资格创建新请求；被拒后重提的实际路径在 2.8 补齐。退出请求终态保留，不能复用旧请求给新报名退出。先到先得/参加审核模式均不改变受限退出需要理由和审批的规则。
