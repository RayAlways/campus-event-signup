## Requirements Inventory

### Functional Requirements

以下保持 PRD 的原编号；每条摘要包含影响后续故事和验收的主要规则。完整业务依据仍为 PRD，不以摘要删减源文。

- **FR-01：注册与登录。**唯一用户名、昵称和密码注册；重复用户名、缺项或错误凭据不建立登录状态。任何已注册用户均可创建活动，不需申请组织者资格；第一版不要求手机号、学号或实名资料。
- **FR-02：退出登录。**退出后原凭据不能继续执行需登录的写操作；旧页面不能绕过服务端身份检查。
- **FR-03：创建和修改草稿。**登录用户只能创建、读取和修改自己的草稿，草稿不公开、不接受报名。容量须为正整数；报名开始＜截止≤活动开始。标题、说明、地点等具体字段及可选结束时间保留 A-4，不把建议字段冒充全部已确认。
- **FR-04：发布及报名模式。**发起者发布合法草稿，选择先到先得或发起者审核；发布后在允许时限内可修改模式，须说明、通知，并按 FR-23 迁移申请，不能仅改字段。
- **FR-05：列表与详情。**未登录可浏览已发布活动及其公开信息，显示时间、模式、容量与真实剩余名额，明确未开始、截止或满额原因；不公开完整名单。取消活动仍在列表，排在所有未取消活动后并标“活动已取消”，详情、取消原因和历史可查，报名入口关闭。若做分页，先全局排序再分页；不要求本版必须做分页。
- **FR-06：修改已发布活动。**仅发起者修改本人活动，变更说明必填，非法修改不产生成功通知；不清退名单或删除历史，容量不得小于成功名单人数（含退出待审者）。开始前可改时间、容量、模式和退出策略；已截止报名不因改期重开。开始后仅可改标题/说明/地点等普通信息及公告，不能改业务设置或取消整场；实际生效时检查时限。
- **FR-07：先到先得报名。**登录用户仅在报名期内报名；有名额且已处理应优先补录的旧候补才成功。满额失败，不新增成功记录；新报名不能插队，同一人不得重复产生有效申请或占位。
- **FR-08：提交参加审核申请。**报名期内提交后为待审核，不占名额；满额仍接收待审申请。截止后不接收新申请，也不删除已有申请；释放名额不使审核模式申请自动通过。
- **FR-09：发起者查看申请。**仅查看自己活动的申请及状态；待审与成功人数分别展示，候补按有效顺序展示，不能把申请总数当成功人数。
- **FR-10：审核通过参加申请。**当前审核模式下，发起者可在活动开始前处理截止前提交的待审申请；有名额才通过，满额失败仍待审。并发通过不超容量；先到先得模式不开放人工插队通过入口。
- **FR-11：拒绝参加申请。**当前审核模式、审核期内仅发起者可拒绝；拒绝不占名额，理由选填，本人可见结果。不能用“拒绝参加”移除已成功者，后者须按退出流程处理。
- **FR-12：撤回未入名单申请。**活动开始前，本人可撤回待审或候补，报名截止后也可撤回；不改变已占名额，撤回记录不再被审核或补录。并发录入若先成功，就按已入名单者的退出策略处理。
- **FR-13：已入名单者退出。**开始前按独立退出策略处理：自由退出直接生效，受限退出须提交理由并获批。真正退出才移出名单并释放一次名额；当前先到先得且有旧候补则按序补录，审核模式不自动通过申请，报名截止不因此延长。
- **FR-14：再次报名及历史。**被拒、撤回或退出后，在仍开放的报名期内可重新申请，保留旧历史，按当前模式和新申请时间处理；不恢复旧排队位置。每人每场最多一条当前有效申请；退出待审仍属成功，不能再占一位。
- **FR-15：本人记录与状态。**本人可查看活动、申请及结果；待审/候补明确提示尚未成功，退出待审同时显示“报名成功、退出待审核”。开始后未处理的申请仍可查并提示处理已截止，不自动批准或递补。
- **FR-16：成功名单。**仅发起者可查看本人活动的成功名单，包含退出待审者，排除未入名单和已经退出者，人数与占位一致；不显示密码等私密账号信息。用户名/昵称/状态的具体最小字段仍按 A-5 复核。
- **FR-17：重复请求与失败反馈。**重复点击或重试不重复申请、占位、释放或通知；失败不产生部分业务变化。未登录、无权、过期、状态冲突或容量不足有明确结果；冲突时返回当前状态并要求刷新，不把失败显示为成功。
- **FR-18：设置退出策略。**退出策略独立于报名模式，两种模式×两种退出策略的四种组合均须可用；详情和本人页面显示退出条件。开始前可改策略，保留既有申请；改自由退出后本人可直接退出，旧请求不能再次释放名额；开始后策略固定、退出关闭。
- **FR-19：退出申请与审核。**受限退出须在开始前提交必填理由，仅本人和发起者可见理由及结果，仅发起者审核。待审仍成功占位；通过才退出，拒绝不释放。开始前可撤回待审退出申请，被拒后可重提，不能有并行有效请求；开始后停止提交、撤回和审核，历史保留，不自动退出。
- **FR-20：活动公告。**仅发起者发布/修改本人活动公告；包含正文与发布时间，更新需说明并按 FR-21 通知，保留变更记录，第一版不硬删除。开始后仍可发布和更新公告。
- **FR-21：站内通知。**活动修改/公告更新或取消须说明，向变更前成功名单生成通知，含退出待审者，不含仅待审/候补者。登录后查看，有未读提示；通知包含活动、类型、说明、时间和入口。每次变更每人最多一条，仅能读和标记本人通知；已读不删除事实，也不代表重新同意变更。取消后仍能读取和标记已读；不要求外部渠道或实时推送。
- **FR-22：整场取消。**仅发起者在开始前填原因取消本人已发布活动；关闭待审参加、候补和待审退出请求，标“因活动取消关闭”，停止报名、参加/退出审核、个人撤回/退出和补录。成功历史不记作主动退出；活动及通知保留，列表沉底。开始时及以后禁止取消；重复取消不重复通知。
- **FR-23：模式切换与公平补录。**审核转先到先得时，成功者不变，有效旧待审按原申请时间优先录入，满额剩余转有序候补；同时间按服务端受理顺序。先到先得切回审核，成功者不变，候补转待审并保留原时间，停止自动通过。自由退出、退出获批或扩容释放名额时，当前先到先得优先补录旧队首，新申请不能插队。开始前可补录，截止后仅处理已有候补；开始/取消后停止。重报用新时间，失效历史不复活，改期不重开截止报名，反复切换不重置有效队列键。

### NonFunctional Requirements

- **NFR-01：名额与状态一致性。**成功响应后始终满足已占人数＝成功名单人数、剩余名额＝容量−已占人数≥0；失败无部分扣位或半成功。验证覆盖最后一席的并发报名/通过，及撤回、切换、补录、退出批准、扩容、取消交错；超额、负数、重复占位/释放、违反旧申请优先的次数目标均为 0。50 并发请求、每模式 20 轮仍是 A-6 验证预算建议，执行前由两位成员确定并记录环境、实际请求、轮次和失败响应，不声称已经测试。
- **NFR-02：身份与资源隔离。**不得明文存储密码或向日志/接口/名单泄露密码；注册登录不获得他人活动管理权。用未登录、参与者、本活动发起者、他活动发起者验证允许/拒绝路径；未经授权写入和他人私密记录泄露目标均为 0。覆盖退出理由、通知、名单与公告管理；退出后旧凭据不能继续写入。
- **NFR-03：正常重启持久性与可复现。**已成功返回的账号、活动、申请和审核、队列顺序、取消及通知已读状态，刷新或正常停止/重启后保留；不能恢复成初始演示数据。保存多状态数据重启比较，由另一成员从干净检出按 README 初始化、启动及验证；异常断电恢复未纳入本次确认范围。
- **NFR-04：变更与通知一致性。**不能变更成功却漏掉原成功名单的通知；失败操作不能生成成功通知，同变更同接收者至多一条，取消原因入口保留。以成功者、退出待审者、参加待审者和候补者验证接收者集合、归属、数量、说明、未读及跨用户隔离；漏通知、重复通知及泄露目标为 0。

### Additional Requirements

AR 编号仅用于本规划中的架构输入追踪，不替代 FR/NFR，不增加用户已批准的业务范围。除 AR-01 中已选高层技术组合外，下述实现机制来自 draft 架构，属于 T-1/T-2 技术建议；故事进入实施前须明确采用状态。

- **AR-01：官方 Starter 及版本种子。**后续首个基础搭建故事应以 Spring Initializr 和 create-vue 为起点。架构已核查 Boot 4.2.0、Java 编译目标 21、Vue 3.5.46、Router 5.5.1、Vite 8.3.8、MySQL 8.4.13.1 等种子；详细版本、BOM、Wrapper 和来源以架构 Stack、version-research.md 为准。实际 JDK 补丁、数据库供应与构建尚未验证，不能把核查写成已安装。
- **AR-02：单体及模块边界（AD-1）。**Vue `/api`→Spring MVC JSON→后端规则；一个应用、一个业务数据库，按 identity/activity/participation/notification 分模块，由应用层协调；前端不裁决身份、名额或时限。
- **AR-03：统一事务和名额真值（AD-2）。**已存在活动的全部业务写先锁活动主键行，同一 Spring JDBC READ_COMMITTED 事务中检查、计数和变更；不独立提交、不持锁调外部服务。名额由 CONFIRMED 计数，不另设可写人数真值；读取容量与人数采用一致快照。
- **AR-04：当前槽位与历史（AD-3）。**活动/用户唯一槽位指向当前报名尝试，重报新建 attempt；退出请求独立，待审不改成功状态。保持指针归属、唯一性和终态不复用；整场取消保留成功历史，未处理请求按取消关闭。
- **AR-05：时间、队列和截止事实（AD-4）。**锁后另取数据库 UTC 时间，分配及最终写前复核，跨适用时限整条回滚；队列键为原提交时间＋活动内受理序号。切换/扩容/真实退出在事务内同步补录，禁止新申请插队；持久保存截止事实，编辑不清除。
- **AR-06：Session、CSRF 与资源权限（AD-5）。**服务端会话、HttpOnly/SameSite Cookie，HTTPS 时 Secure；登录轮换、退出失效，保留 CSRF，密码单向编码。身份取会话，按 owner/user/recipient 校验资源，不采信客户端 actorId；公告与说明按纯文本展示。
- **AR-07：通知同事务（AD-6）。**先快照原成功名单，再写变更、不可变历史与去重站内通知；失败整体回滚，不仅依赖提交后异步监听。通知不含退出私密理由；已读只影响本人通知。
- **AR-08：基础接口契约（AD-7）。**状态枚举统一，JSON camelCase，BIGINT 标识/序号传字符串，UTC ISO-8601 时间、页面北京时间；统一成功/错误结构和实际 HTTP 状态，不能由前后端分别发明字段或状态。
- **AR-09：版本与幂等（AD-7）。**编辑和已有申请操作核对对象版本；活动命令成功回执与业务同事务，按用户＋幂等键唯一。同键同载荷重放、不同载荷拒绝，旧请求不影响新 attempt；失败/锁超时/死锁不留下部分变更，重试重新检查时限。
- **AR-10：迁移及持久化（AD-8）。**Flyway 是结构迁移入口，不改写已共享迁移；MySQL 保存业务，启动不清表或覆盖演示数据；开发/测试数据库分离。
- **AR-11：构建和交付（AD-8）。**开发时 Vite 代理，交付时 Vue 构建物由 Boot 同源提供，API 404 不能落入 SPA 路由回退。单实例，不以 Redis 或消息队列为前提；会话重启失效可重新登录，但业务数据须保留。
- **AR-12：真实数据库验证（AD-8）。**集成和并发验收使用固定目标版本的真实 MySQL、独立测试库，不能以 H2/Mock 代替一致性证据；环境、依赖解析及运行命令在实际搭建后记录。
- **AR-13：依赖及前端语言建议。**后端传递依赖由固定 Boot BOM 管理，前端提交 lockfile、使用 npm ci；JavaScript 为 T-2 建议，不把未选的 TypeScript/latest Vitest 或可选 Pinia 加成架构前提。
- **AR-14：单一详细接口契约。**后续对应故事并行开发前，由后端起草、另一成员核对完整端点和字段；架构建议的 docs/api-contract.md 当前尚未创建，不当作已有文件引用。
- **AR-15：配置与日志。**示例配置不含真实密码；日志可关联 requestId/commandId/活动标识，但不记录密码、会话令牌或退出理由；未经授权失败不返回 SQL 内部细节。
- **AR-16：运行与运维边界。**环境故事确定 JDK 发行版/补丁、数据库安装包或镜像及 CI 供应方式；若需公网试用再明确 TLS/托管和备份。当前没有部署、高可用或实测性能承诺。

## Epic List

**状态：用户已于 2026-11-26 确认分组。**三个史诗均按用户结果贯穿页面、接口、数据、权限及适用验证。当前进入故事创建，至少 12 个故事及其 Given/When/Then AC 尚待起草和审阅。

### Epic 1: 进入系统并发布、发现活动

**用户结果：**组织者可以注册登录、保存自己的活动草稿、设置初始报名模式与退出策略并发布活动；同学无需登录即可浏览公开活动及参与条件。交付后得到可使用的活动发布与发现流程。

**FRs covered（主责）：**FR-01、FR-02、FR-03、FR-04、FR-05、FR-18。FR-17 的适用失败反馈随这些入口实现；后续变更和取消场景按覆盖表由 Epic 3 补齐。

**范围边界：**不宣称已经可以报名或审核，也不开放尚未交付的发布后模式切换、公告更新或取消入口。没有 Epic 2/3 时，账号与活动目录仍可正常使用，不依赖未来代码或假成功接口。

**实现与验证考虑：**官方脚手架、数据库迁移、基础契约和身份保护为该用户流程提供支撑，不分别建成“数据库”“后端”“前端”史诗。只建立当前所需结构；字段与环境保留项在对应实施前复核。验证登录/退出、草稿隔离、合法发布、公开详情及正常重启持久性。

**依赖：**无其他产品史诗前置；软件环境实际搭建仍待执行。

### Epic 2: 完成报名、审核与退出

**用户结果：**参与者可以对已发布活动直接报名或提交审核申请，查看结果，撤回未入名单申请；入名单后按活动策略自由退出或提交理由请求退出。组织者可以审核自己活动的参加/退出申请并掌握有效名单。被拒、撤回或退出后，可在报名期内重新申请并保留历史。

**FRs covered（主责）：**FR-07、FR-08、FR-09、FR-10、FR-11、FR-12、FR-13、FR-14、FR-15、FR-16、FR-17、FR-19；落实 FR-18 的两种报名模式×两种退出策略组合。

**范围边界：**本史诗在“当前活动设置保持不变”的条件下提供完整参与流程；报名截止后审核/撤回和活动开始后的停止规则仍然生效，不因分阶段而裁掉。未交付模式迁移时不会产生其候补队列；涉及候补、改策略、改期和整场取消的增量由 Epic 3 接入。这里不新增“参加结果必须通知”等源需求未要求的渠道或消息规则。

**实现与验证考虑：**报名与退出共享容量真值和状态模型，集中在同一史诗，避免把四种策略组合拆到不同技术层。按已选设计或后续审阅结果验证最后一席、重复审核、退出待审占位、旧请求不能影响重报、理由/名单隐私与状态持久性。

**依赖：**Epic 1 的账号、活动发布与详情；不需要 Epic 3 的变更、候补或通知功能才能使用上述流程。

### Epic 3: 管理活动变更、公平补录与通知

**用户结果：**组织者可以在规则允许的时段修改已发布活动、报名模式和退出策略，发布公告或取消整场活动；原名单成员能查看变更通知。已有申请在模式切换后保持公平顺序，有空位时旧候补按序录入；取消活动保留历史、沉底并说明原因。

**FRs covered（主责）：**FR-06、FR-20、FR-21、FR-22、FR-23。增量完成 FR-04、FR-05、FR-07、FR-09、FR-10、FR-12 至 FR-19 中涉及模式迁移、候补、策略修改、改期或整场取消的场景，详见 FR 覆盖表。

**范围边界：**变更、说明、通知和必要的状态迁移作为同一业务能力完整交付，不能先开放编辑再等未来史诗补通知。开始后只改普通信息和公告，不能改业务设置或取消整场；截止后不收新申请但开始前可补录已有候补。保留取消活动与原成功历史，不用删除或主动退出代替取消。

**实现与验证考虑：**已发布变更会同时影响容量、队列、退出请求、接收者和历史，集中到一个史诗处理，避免在多个史诗反复改同一规则。验证双向迁移、时间边界、扩容/退出后的补录、候补撤回竞争、变更与通知原子性、重试去重和取消后的只读历史。全部前两史诗已适用行为须回归，不能为新流程破坏旧流程。

**依赖：**Epic 1 的已发布活动、Epic 2 的申请/成功名单/退出状态；没有对未来史诗的依赖。
