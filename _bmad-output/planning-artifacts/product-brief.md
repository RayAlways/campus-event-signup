# 班级与社团活动报名管理产品简报

日期：2026 年 11 月 25 日

状态：初稿，项目约束与报名规则已确认，用户问题尚待验证。

## 产品目标

为班级或社团的小型活动提供一个集中处理发布、限额报名、取消报名及名单查看的系统。两人团队在 2026 年 12 月 9 日前完成课程要求的 BMAD 与敏捷过程产物，并交付能按 README 运行和验证的实现。

业务范围应支持至少 3 个史诗、12 个可独立验收的故事；正式故事划分在架构设计后完成。产品复杂度集中于限额报名的一致性以及角色权限，避免扩展到与本次目标无关的业务。

## 问题假设

待验证的问题是：小型活动的组织者需要可靠地限制报名人数、掌握有效名单；参与者需要明确知道自己是否报名成功，并能取消报名。若现有流程依赖分散消息或人工维护，可能出现名单更新不及时、重复记录或超额报名。

以上关于现有流程与痛点的描述是假设。尚未确认具体班级或社团、现用工具、活动频次、人数规模或实际出错案例，不据此声称已经开展用户调研。

## 目标用户与使用情境

| 角色 | 期望完成的事情 | 需要核实的信息 |
|---|---|---|
| 活动组织者 | 发布带容量和报名时间的活动，查看有效名单 | 谁能组织活动、常见名额、名单需要哪些字段 |
| 活动参与者 | 查看活动、报名、取消、查看自己的状态 | 使用设备、身份识别方式、取消限制 |

拟覆盖一个班级或一个社团的活动试用场景。是否面向多个组织、是否需要独立平台管理员，留待 PRD 明确；当前不承诺多组织平台能力。

## 第一版范围草案

以下能力用于界定范围，尚未代替正式史诗与用户故事。

| 能力范围 | 第一版拟包含 |
|---|---|
| 活动管理 | 组织者创建、编辑、发布活动；参与者查看列表与详情；展示容量和报名时间 |
| 报名与名额控制 | 先到先得报名、重复报名处理、取消并释放名额、满额反馈、并发争抢处理 |
| 名单与权限 | 区分组织者与参与者，查看本人报名记录，组织者查看其负责活动的有效名单，限制越权访问 |

## 已确认与待确认的业务边界

已经确认：报名先到先得，有名额则成功；取消报名释放名额。

以下规则应在 PRD 中逐项明确，当前不能作为已确认需求：

- 报名是否有开始与截止时间，截止后是否允许取消。
- 取消后能否再次报名，以及名额计数和历史记录的处理方式。
- 同一用户的重复点击或网络重试如何返回结果。
- 活动已经有人报名后，容量、时间等字段允许如何修改。
- 参与者如何注册或登录，组织者身份由谁分配。
- 是否存在匿名查看、成员资格限制或仅限本班参与的条件。

## 非功能需求方向

PRD 至少应形成两条可测量的非功能需求。以下为拟采用的验证方向，尚未完成编号、测试环境和阈值定义。

| 方向 | 拟验证行为 |
|---|---|
| 并发一致性 | 当活动只剩 1 个名额时，多名不同用户同时报名，最多 1 人成功；有效报名数不超过容量，剩余名额不为负 |
| 访问控制 | 普通参与者不能调用活动管理接口、修改他人报名或读取其无权查看的完整名单；直接请求接口也受到同样约束 |

真实业务规模尚未核实，不把某个并发数或响应时间写成用户已经提出的要求。测试并发数、重复次数和执行环境在 PRD 中确定并保存结果。

## 成功度量草案

以下指标是建议目标，用户试用规模与验收方法仍需团队确认。

| 指标 | 建议验收方法 |
|---|---|
| 核心流程完整 | 用预置数据完成发布、报名、取消、再次报名、名单查看全过程，并有对应测试 |
| 名额不会超卖 | 并发测试确认容量约束成立，同时核对数据库中的有效报名记录 |
| 权限边界明确 | 对普通用户、组织者及未登录访问分别执行允许与拒绝用例 |
| 真实可用性 | 邀请至少 1 位组织者和 1 位参与者试用，记录任务结果、反馈与因此发生的调整；未开展前保持待完成状态 |
| 可复现交付 | 另一位成员从干净检出开始，按 README 启动并完成测试，记录环境与问题 |

课程过程的完成度另见作业要求核对表，不能用文档数量替代用户价值验证。

## 第一版暂不包含

为控制两人团队的工作量，建议排除支付、退款、短信或微信通知、微信小程序、候补队列、复杂审批、签到积分、推荐算法、大型多租户管理、原生移动应用和高并发分布式部署。若后续用户验证显示某项必不可少，应先评估范围和工期，再记录决定。

## 团队与技术约束

项目实际为 2 人，准备与实施时间约两周。课件原定 3–4 人组队，人数差异尚未获知老师明确认可，不把两人组队写成已批准的例外。

优先比较 Java 实现方案，因为发起人已有相关基础。框架、数据库、页面方案、认证方式及部署方式均未选定。架构阶段应结合另一位成员的能力、运行便利性与一致性要求比较方案，至少记录 5 条 ADR 及其被否决的备选方案和理由。

## 用户验证准备

首次沟通应核实以下内容，保留匿名化记录即可：

1. 最近一次活动是什么，多少人参与，如何发布和收集报名。
2. 当前流程中实际出现过什么问题，是否确有名额限制。
3. 取消、重新报名、截止时间与组织者修改活动的实际规则。
4. 组织者需要查看哪些名单字段，参与者可以看到什么。
5. 是否愿意试用，能否提供一个不涉及敏感信息的活动案例。

如果无法联系到真实使用者，应如实保留这一状态并继续寻找可验证场景，不编造访谈、评价或试用结果。
