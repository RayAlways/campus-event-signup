# 班级与社团活动报名管理 PRD

本需求规格供两人团队确认范围，并供后续架构、史诗、故事和测试引用。采用用户选择的“快速初稿”方式：已确认规则与 `[ASSUMPTION A-n]` 建议分开记录，待用户审阅后再冻结需求。当前为草稿，不代表已经实现、测试或完成真实用户验证。

## 1 产品目标与依据

为班级或社团的小型活动提供统一的发布、限额报名、审核、受控退出、公告与站内通知。普通活动可先到先得，需要筛选的活动由发起者审核。发起者可修改已发布活动及报名模式，切换为先到先得时须照顾早先有效申请的时间顺序。系统应明确区分参加申请、报名成功和退出申请，在模式切换、退出审核与补录并发时保持名单和名额正确。

这是待真实使用者验证的问题方向。当前没有具体班级或社团的访谈、规模统计或试用记录，不声称已经证明上述痛点。产品形态暂按浏览器网页起草 `[ASSUMPTION A-1]`；Java 是已知团队技术基础，框架、数据库和页面方案留待架构阶段比较。

依据为 [产品简报](../../product-brief.md)、[决策日志](../../../../decision-log.md) 和本次用户回答。课程交付要求另见 [核对表](../../../../docs/assignment-checklist.md)，不把文档数量或实验要求混写为软件功能。

本次用户新增确认：

- 注册登录后，任何用户都可发起活动或报名；只能管理自己发起的活动。
- 截止前提交的申请，报名截止后仍可审核，但须在活动开始前完成。
- 审核模式满额后仍接受申请；申请保持待审核、不占名额，不会自动转为通过。
- 活动开始前，尚未进入名单的申请可随时撤回；已进入名单者按发起者设置直接退出，或提交必填理由的退出申请，获批后退出。
- 发布后允许修改报名模式、活动信息与公告；活动修改、取消须说明情况，通过站内通知告知名单内用户，并提供未读提示。
- 审核切为先到先得时，早先有效申请按原申请时间优先录入；满额时保留顺序，空位出现后自动补录。

## 2 用户与范围

活动发起者和报名者是用户在某场活动中的身份，不是注册时固定分配的两类账号。同一用户可以管理自己发起的活动，也可以参与其他活动。审核由活动发起者单级完成；暂不设置独立平台管理员是初稿的范围建议 `[ASSUMPTION A-8]`。

第一版覆盖注册登录、活动发布与修改取消、两种报名方式、参加审核、退出策略与退出审核、切换模式后的顺序补录、公告、站内通知及本人状态和名单。未登录用户能否浏览活动尚未确认，初稿建议允许浏览已发布活动，写操作必须登录 `[ASSUMPTION A-2]`。

实名资料、申请材料、审核标准及一次真实使用过程尚未提供。暂不编造命名人物或访谈型用户旅程；本稿的行为示例仅用于验收设计。

## 3 术语与不变量

| 术语 | 定义 |
|---|---|
| 用户 | 拥有登录账号的人；身份与权限按当前活动及操作判断 |
| 活动发起者 | 创建该活动的用户；仅其可管理和审核该活动 |
| 报名模式 | 每场活动当前采用先到先得或发起者审核；发起者可在发布后修改 |
| 容量 | 活动允许同时处于“报名成功”的人数，必须为正整数 |
| 报名记录 | 某用户对某活动的一次报名或申请及其当前状态 |
| 待审核 | 参加申请已提交但尚未通过；不占名额。与“退出申请待审核”不同 |
| 候补 | 审核切为先到先得后，按原申请时间排序但尚未入名单的有效申请；不占名额，可在空位出现后自动补录 |
| 报名成功 | 直接报名成功或审核通过；占用一个名额 |
| 退出策略 | 与报名模式独立：允许自由退出，或退出须由发起者审核 |
| 退出申请 | 已在名单中的报名者提交的退出请求及理由；审核期间报名仍成功、仍占名额，不将其改成未占位的参加申请 |
| 已拒绝、已撤回、已退出 | 参加失败、撤回未入名单申请或完成退出的非成功状态，不占名额；“已退出”取代旧草稿中参与者“已取消”的叫法 |
| 活动已取消 | 发起者取消整场活动，区别于个人退出；历史保留与申请关闭细节见 A-10 |
| 报名期 | 报名开始时间 ≤ 系统当前时间 < 报名截止时间 |
| 审核期 | 报名开始时间 ≤ 系统当前时间 < 活动开始时间；仅处理已提交申请 |

始终满足：`已占名额 = 当前报名成功记录数`，`剩余名额 = 容量 − 已占名额 ≥ 0`。待审核人数不计入已占名额。具体如何实现原子性由架构决定。

活动至少区分草稿和已发布；“报名未开始、报名中、报名已截止、活动已开始”可根据时间判断，不要求增加后台定时任务。初稿建议 `报名开始时间 < 报名截止时间 ≤ 活动开始时间`，若填写活动结束时间则 `活动开始时间 < 活动结束时间`；不允许零长度报名期，页面时间统一按 Asia/Shanghai 展示并以系统时间判断边界 `[ASSUMPTION A-4]`。

按 A-4 的建议，时间条件在服务端执行业务状态变更时判断，不能仅信任页面按钮或客户端传入时间。

## 4 功能需求

### 4.1 账号

#### FR-01 注册与登录

用户可注册并登录，获得本人身份。初稿建议使用唯一用户名、昵称和密码，不收集手机号、学号或实名资料 `[ASSUMPTION A-5]`。

- 相同用户名不能注册两个账号；缺少必填项或凭据错误时不建立登录状态。
- 注册成功的用户均可创建活动；不存在“先申请组织者资格”的隐含门槛。

#### FR-02 退出登录

用户可退出登录。

- 退出后，原登录凭据不能继续执行报名、创建或审核等需登录操作。
- 客户端保留旧页面也不能绕过服务端身份校验。

### 4.2 活动发布

#### FR-03 创建与修改草稿

登录用户可创建、保存和修改自己的活动草稿。初稿字段为标题、说明、地点、容量、报名起止时间、活动开始时间和报名模式 `[ASSUMPTION A-4]`。

- 容量为 0、负数或非整数时不能发布；必要字段缺失时不能发布。
- 按 A-4 的建议，报名开始等于或晚于截止、截止晚于活动开始、结束不晚于开始时均拒绝发布；报名截止等于活动开始允许，但不会留下截止后的审核窗口。
- 他人不能读取或修改草稿；草稿不出现在公开的已发布活动列表。

#### FR-04 发布及报名模式

活动发起者可发布合法草稿，并选择一种报名模式。

- 发布后活动出现在已发布列表，报名方式可见；草稿不能接受报名。
- 发布后允许由发起者修改报名模式，必须填写变更说明，并按 FR-21 通知名单内用户；不得仅修改字段而跳过 FR-23 的申请迁移和顺序处理。

#### FR-05 活动列表与详情

用户可查看已发布活动的标题、说明、地点、发起者、时间、模式、容量及剩余名额。

- 报名未开始、已截止或满额时显示相应原因；审核活动满额不等同于停止接收申请。
- 详情中的剩余名额以报名成功数计算，不能减去待审核人数；不公开完整报名名单。

#### FR-06 修改已发布活动

活动发起者可修改本人已发布活动的相关信息及报名模式，必须填写变更说明，并产生 FR-21 的站内通知。公告按 FR-20 管理，整场取消按 FR-22 管理。

- 变更说明为空或字段非法时拒绝修改。由第 3 节容量不变量导出：容量也不能改到低于当前名单人数（包括退出申请待审者），否则拒绝且不发送成功通知；这是保持一致性的约束，不冒充用户单独提出的缩容细则。
- 名单和历史不得因编辑被静默删除；报名模式变更按 FR-23 处理，不清退已经成功入名单者。
- 修改时间、容量或退出策略对已有申请的影响及允许修改的时限，留待 A-9 明确；不能把未确认细则写成已确定规则。硬删除历史记录不等于取消活动。

### 4.3 两种报名模式

#### FR-07 先到先得报名

登录用户在报名期内可报名已发布的先到先得活动。

- 有剩余名额且没有按 FR-23 应优先补录的早先申请时，产生报名成功记录；不得让新报名越过有效候补。没有可分配名额时失败，不新增成功记录。
- 同一用户已有待审核、候补或报名成功记录时不新增第二条有效记录；重复操作遵循 FR-17。
- 报名开始前、报名截止时及以后，均不能新报名。

#### FR-08 提交审核申请

登录用户在报名期内可对审核模式活动提交申请。

- 提交成功后为待审核，不是报名成功，也不占名额。
- 即使剩余名额为 0，仍可提交待审核申请；有人取消或释放名额时，不自动转为通过。
- 报名截止后不再接收新申请，但不因此删除此前提交的待审核记录。

#### FR-09 发起者查看申请

活动发起者可查看本人活动的参加申请及其状态；候补顺序按 FR-23 展示。

- 仅看到自己活动的待审核、报名成功、已拒绝及已撤回等记录；他人活动不在管理范围。
- 待审核人数和报名成功人数分别显示，不能把全部申请数当成已报名人数。

#### FR-10 审核通过

活动发起者在当前为审核模式且处于审核期时可通过待审核申请，每次通过仍受容量约束；当前为先到先得时由 FR-23 统一处理迁移后的顺序，不另开人工插队入口。

- 报名截止后、活动开始前，仍可通过此前提交的申请；活动开始时及以后不能通过。
- 有名额时，待审核转为报名成功，只占用一次名额；并发处理不超出容量。
- 初稿建议容量不足时操作失败、记录仍为待审核，向发起者说明名额不足 `[ASSUMPTION A-3]`。

#### FR-11 审核拒绝

活动发起者在当前为审核模式且处于审核期时可拒绝参加申请。拒绝参加与拒绝退出申请是不同操作。

- 拒绝后状态为已拒绝，不产生成功报名，也不改变已占名额；报名者能查看结果。
- 参加申请的拒绝理由是否必填仍待确认 `[ASSUMPTION A-3]`。已成功入名单者的退出应走 FR-13、FR-19，不能通过拒绝参加申请移出名单。

### 4.4 撤回、退出与重复操作

#### FR-12 撤回待审核申请

用户已确认：报名者在活动开始前可随时撤回本人尚未进入名单的参加申请，包括报名截止之后的待审核申请。切换模式后仍未入名单的候补同样可撤回。

- 撤回后为已撤回，名额不变；该条申请不能再被通过或自动补录。
- 与审核或补录并发时，只能生效一个符合前置状态的变化；若录入先成功，用户须按 FR-13 的退出策略处理，不能继续使用免审批的撤回路径。

#### FR-13 已入名单者退出

活动开始前，报名成功的用户无论通过何种报名模式进入名单，均按活动的退出策略处理。

- 允许自由退出：用户可直接退出，状态为已退出，移出当前名单并释放恰好一个名额。
- 限制自由退出：用户提交退出申请及理由，按 FR-19 由发起者审核；仅提交请求不移出名单、不释放名额。
- 真正释放名额后按当前模式处理：先到先得模式优先执行 FR-23；审核模式不自动通过参加申请。报名截止不会因退出而延期。

#### FR-14 再次报名与历史

用户本次尚未确定重报规则。初稿仍建议已拒绝、已撤回或已退出后，在报名期内可重新报名或申请，并保留前次处理历史 `[ASSUMPTION A-3]`。

- 新一轮按活动当前模式、容量及有效候补顺序处理；不能绕过报名截止，也不能继承已撤回或已退出申请的旧排队位置。
- 同一用户对同一活动最多一条当前待审核、候补或报名成功记录；历史已退出记录不占位。退出申请待审时仍属报名成功，不能重新占位。

#### FR-15 查看本人记录

用户可查看本人报名和申请的活动、当前状态与结果。

- 待审核与候补明确提示“尚未报名成功”；已拒绝、已撤回、已退出不得显示为成功。退出申请待审时同时显示“报名成功、退出待审核”，避免用户误以为已经退出。
- 活动开始后仍未处理的申请保留可查，并提示审核已截止；不要求自动批准、候补递补或后台清理。

#### FR-16 查看活动成功名单

活动发起者可查看本人活动当前报名成功的用户名单。

- 名单不含待审核、候补、已拒绝、已撤回、已退出记录；包含退出申请待审者，人数与详情的已占名额一致。
- 初稿仅向发起者展示用户名、昵称和报名状态，不展示密码或其他账号私密信息 `[ASSUMPTION A-5]`。

#### FR-17 重复请求与失败反馈

系统应对重复点击、失效操作和业务失败返回明确结果，不因重复请求产生重复状态变化。

- 活跃记录的重复报名或申请返回已有状态或明确的重复提示，不新增一条活跃记录；重复通过或取消不重复扣减或释放。
- 未登录、无权操作、非当前状态、时间已过、容量不足等失败均不改变业务数据；报名者和发起者看到的结果不能互相矛盾。
- 状态冲突时返回当前状态，要求用户刷新后选择仍有效的操作，不把失败伪装为成功。

### 4.5 退出审核与活动变更

#### FR-18 设置退出策略

发起者为活动设置允许自由退出或退出须审核；该设置独立于先到先得或参加审核模式，四种组合均须可用。

- 活动详情和本人报名页应明确显示退出条件，不把“先到先得”默认解释成可自由退出。
- 发布后修改退出策略的适用范围、既有退出申请如何衔接仍属 A-9，不静默清除申请。

#### FR-19 提交和审核退出申请

限制自由退出的活动，已入名单者在活动开始前可提交本人退出申请，退出理由必填；仅活动发起者能审核。

- 待审期间维持报名成功、占用名额；批准后才移出名单并释放一次名额。拒绝后仍在名单且继续占位。
- 重复提交不得产生并行的有效退出申请；重复通过不得重复释放或重复补录。退出理由及结果仅本人和发起者可见。
- 审核退出的截止时间、能否撤回退出申请及拒绝后再次提交规则仍待 A-9 确认，不与参加申请的审核规则混为一谈。

#### FR-20 活动公告

发起者可发布、修改本人活动的公告；其他用户不能代发或修改。

- 公告有正文及可识别的发布时间；活动信息修改、公告更新须有情况说明，通知按 FR-21 执行。
- 用户可在活动详情查看当前公告；历史版本或是否允许删除公告留待 A-9 确认。

#### FR-21 站内通知

修改或取消已发布活动时，发起者须填写说明，系统向当时已在活动名单中的用户生成站内通知，登录后可查看并有未读提示；站内通知不要求邮件、短信、微信或实时推送。

- 通知包含活动标识、变更或取消类型、情况说明、时间及查看活动的入口；用户只能读取和标记本人通知。
- 接收对象取变更生效前的成功名单，含退出申请待审者；取消时不能先清空名单再计算接收者。仅待审核或候补者不计为已入名单用户。
- 同一次成功变更对每个接收者只生成一条通知；重复请求不得重复群发。标记已读不删除变更事实，不代表用户重新同意活动修改。

#### FR-22 发起者取消活动

发起者可说明原因后取消本人已发布活动，并按 FR-21 通知原名单用户。

- 取消后停止新报名、参加审核、退出审批与候补补录，不再因释放名额继续录入；历史信息与通知入口保留，不能以物理删除冒充取消。为避免在已取消活动上继续改变名额，草稿还建议停止个人撤回、自由退出及新退出请求 `[ASSUMPTION A-10]`，具体记录终态仍待确认。
- 取消原因为空或他人发起取消时拒绝操作；重复取消不重复通知。
- 已有报名记录、待审和退出申请的具体终态映射及允许取消的时限仍待 A-10 确认。

#### FR-23 切换模式与按序补录

用户明确否决“旧待审继续人工审核、新报名直接抢位”的迁移建议。审核切为先到先得时，仍有效的旧待审核申请按原提交时间优先依次入名单，直到满额；剩余申请保留原顺序作为候补，后续空位自动按序补录。

- 已成功入名单者保留名额；已撤回、已拒绝、已退出的历史记录不重新参加排序。同一申请时间相同时，建议采用稳定的服务端受理次序而非随机打乱 `[ASSUMPTION A-10]`；原申请时间优先和持续补录本身已获用户确认。
- 有有效候补时，新报名不能越过队列；通过自由退出、退出获批或扩容产生的空位，优先分配给队首有效申请。退出申请尚未获批不产生空位。
- 补录成功才占位；并发切换、扩容、退出审核、新报名和补录仍须满足容量不变量，不得同一人多次入名单。
- 切回审核模式时不自动批准旧申请；候补如何转回待审核、报名截止后的补录时限以及活动改期对这些条件的影响，列入 A-10 待确认。活动已取消时任何队列都不得继续补录。

## 5 状态与边界走查

以下仅为验证规则的测试场景，不是已完成测试或来自真实使用者的旅程记录。

| 场景 | 应有结果 |
|---|---|
| 先到先得只剩 1 位，两位不同用户同时报名 | 最多一位新增报名成功，其余失败；剩余名额不为负 |
| 审核模式已有 10 条待审核、容量为 1 | 待审核不占位；只能通过一位，其他不会自动通过 |
| 审核模式满额时有新申请 | 接收为待审核；成功名单和已占名额不变 |
| 截止前申请，截止后但开始前审核 | 允许；到活动开始时间后禁止处理 |
| 他人伪造活动或申请标识提交审核 | 拒绝；数据不变，不泄露完整名单 |
| 退出须审核，用户提交退出请求 | 仍在名单中、仍占名额，不能提前补录其他人 |
| 退出获批，先到先得模式存在候补 | 释放一个名额并按原申请时间补录队首，人数不超容量 |
| 审核切为先到先得，同时有新报名 | 旧有效申请先按时间处理，新报名不能插队 |
| 修改或取消活动 | 必填说明，原名单（含退出待审者）收到一条可读的站内通知 |
| 重复批准退出或重复取消整场活动 | 不重复释放、补录或发送通知 |

## 6 非功能需求

### NFR-01 名额与状态一致性

任意成功响应后的状态必须满足第 3 节不变量，失败操作不产生部分扣位或半成功状态。

验证建议 `[ASSUMPTION A-6]`：在每轮重置数据的条件下，以 50 个并发请求争抢最后 1 位，先到先得和审核通过各重复 20 轮；另交错执行撤回、模式切换、按序补录、自由退出、退出批准、扩容与活动取消。核对名单、队列和名额，超额、负数、重复占位或释放、违反旧申请优先顺序的次数均须为 0。测试报告记录实际环境、请求数、轮数及失败响应，不以请求全部成功为目标。

### NFR-02 身份与资源隔离

注册或登录不赋予管理他人活动的权限。密码不得以明文保存或出现在日志、名单及接口响应中；具体认证、密码保护和会话实现由架构决定。

验证：使用未登录用户、报名者、活动发起者、另一活动发起者直接请求各类管理、审核、个人记录和名单操作。未经授权的写操作成功数及他人私密记录泄露数必须为 0；退出登录后原凭据不能继续写入。每类允许及拒绝路径都保留验证证据。

上述隔离同样覆盖退出理由、退出审核、公告、活动取消与通知；用户不能读取他人的站内通知或退出理由。

### NFR-03 状态持久性与可复现

初稿建议：已经明确返回成功的注册、活动发布与修改、报名、参加/退出审核、候补顺序、活动取消及通知已读状态，刷新页面或正常重启应用后保持一致，不能恢复到示例初始数据 `[ASSUMPTION A-7]`。

验证建议同属 A-7：保存含各种状态的数据，正常停止并重启，再比较用户、活动、当前状态、成功名单及容量，不得丢失已确认数据；异常断电恢复暂不列入目标。另按课程要求，由另一位成员从干净检出开始按 README 初始化、启动并运行验证，不假设其已有本机未提交配置。

### NFR-04 变更与通知一致性

系统不能返回活动修改或取消成功，却漏掉本次原名单接收者的站内通知；失败或未生效的操作不得生成“变更成功”通知。同一变更对同一接收者最多一条，取消后的通知入口仍可查看取消原因。

验证：以多名报名成功者、退出待审者、仅参加待审者和候补者准备数据，分别修改、取消及重试请求，对照原名单逐一检查通知归属、数量、说明与未读状态，并验证他人不能读取。通知如何持久化、与业务变更如何保持一致留给架构方案决定。

## 7 成功指标与取舍

- **SM-01 核心行为正确**：FR-01 至 FR-23 的适用验收条件全部通过；依赖假设的条件须先由用户确认后才能计为通过。目标是可复现的正确结果，不是页面数量。
- **SM-02 名额正确**：NFR-01 指定验证中不变量违规次数为 0，同时说明实测条件；测试通过不等于证明所有运行条件均无缺陷。
- **SM-03 权限正确**：NFR-02 的未经授权写入和信息泄露均为 0；允许路径也必须能正常完成。
- **SM-04 真实可用性**：争取至少 1 位潜在发起者和 1 位参与者试用并记录结果与反馈；这是尚未完成的目标，不写成已经获得用户认可。
- **SM-05 通知正确**：NFR-04 中原名单用户漏通知、跨用户泄露及同一事件重复通知次数均为 0。

反向约束：不追求审核通过率、报名总量或待审核数量越高越好；不能为了让数据好看而把待审核计为成功、隐藏失败请求或省略权限检查。

## 8 第一版边界与课程约束

两种模式、受控退出、顺序补录、活动修改取消、公告、站内通知及资源权限属于核心范围。短信、微信、邮件等外部通知未被要求，本次只采用站内渠道。建议不做支付退款、小程序、原生移动应用、多级审批、会签、自定义审批流程、积分签到、推荐、大型多租户平台及分布式高并发部署；这些范围裁剪仍待审阅 `[ASSUMPTION A-8]`。本次用户已明确纳入的候补和退出审核不得再列作排除项；退出审核不等于多级审批。

项目截止日为 2026 年 12 月 9 日，实际为两人。正式史诗与至少 12 个故事在架构后拆分；本稿不提前指定技术栈、数据库事务或接口方案。后续建立 FR、ADR、故事与测试的编号引用。实验 A、两次冲刺、真实决策日志、AI 声明等继续作为课程过程要求管理，实验 B 按老师说明不做。
