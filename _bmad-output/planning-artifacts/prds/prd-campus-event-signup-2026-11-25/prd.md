# 班级与社团活动报名管理 PRD

本需求规格供两人团队确认范围，并供后续架构、史诗、故事和测试引用。采用用户选择的“快速初稿”方式：已确认规则与 `[ASSUMPTION A-n]` 建议分开记录，待用户审阅后再冻结需求。当前为草稿，不代表已经实现、测试或完成真实用户验证。

## 1 产品目标与依据

为班级或社团的小型活动提供统一的发布、限额报名、审核和名单管理。普通活动可先到先得，需要筛选的活动由发起者审核。系统应明确区分“申请已提交”和“报名成功”，并在并发报名或审核时保持名额正确。

这是待真实使用者验证的问题方向。当前没有具体班级或社团的访谈、规模统计或试用记录，不声称已经证明上述痛点。产品形态暂按浏览器网页起草 `[ASSUMPTION A-1]`；Java 是已知团队技术基础，框架、数据库和页面方案留待架构阶段比较。

依据为 [产品简报](../../product-brief.md)、[决策日志](../../../../decision-log.md) 和本次用户回答。课程交付要求另见 [核对表](../../../../docs/assignment-checklist.md)，不把文档数量或实验要求混写为软件功能。

本次用户新增确认：

- 注册登录后，任何用户都可发起活动或报名；只能管理自己发起的活动。
- 截止前提交的申请，报名截止后仍可审核，但须在活动开始前完成。
- 审核模式满额后仍接受申请；申请保持待审核、不占名额，不会自动转为通过。

## 2 用户与范围

活动发起者和报名者是用户在某场活动中的身份，不是注册时固定分配的两类账号。同一用户可以管理自己发起的活动，也可以参与其他活动。审核由活动发起者单级完成；暂不设置独立平台管理员是初稿的范围建议 `[ASSUMPTION A-8]`。

第一版覆盖注册登录、活动草稿与发布、列表与详情、两种报名方式、单级审核、撤回或取消、本人状态和发起者名单。未登录用户能否浏览活动尚未确认，初稿建议允许浏览已发布活动，写操作必须登录 `[ASSUMPTION A-2]`。

实名资料、申请材料、审核标准及一次真实使用过程尚未提供。暂不编造命名人物或访谈型用户旅程；本稿的行为示例仅用于验收设计。

## 3 术语与不变量

| 术语 | 定义 |
|---|---|
| 用户 | 拥有登录账号的人；身份与权限按当前活动及操作判断 |
| 活动发起者 | 创建该活动的用户；仅其可管理和审核该活动 |
| 报名模式 | 每场活动二选一：先到先得或发起者审核；发布后固定 |
| 容量 | 活动允许同时处于“报名成功”的人数，必须为正整数 |
| 报名记录 | 某用户对某活动的一次报名或申请及其当前状态 |
| 待审核 | 已提交申请但尚未通过；不占名额 |
| 报名成功 | 直接报名成功或审核通过；占用一个名额 |
| 已拒绝、已撤回、已取消 | 初稿中的非成功状态，均不占名额；撤回与取消细则见 A-3 |
| 报名期 | 报名开始时间 ≤ 系统当前时间 < 报名截止时间 |
| 审核期 | 报名开始时间 ≤ 系统当前时间 < 活动开始时间；仅处理已提交申请 |

始终满足：`已占名额 = 当前报名成功记录数`，`剩余名额 = 容量 − 已占名额 ≥ 0`。待审核人数不计入已占名额。具体如何实现原子性由架构决定。

活动至少区分草稿和已发布；“报名未开始、报名中、报名已截止、活动已开始”可根据时间判断，不要求增加后台定时任务。初稿建议 `报名开始时间 < 报名截止时间 ≤ 活动开始时间`，若填写活动结束时间则 `活动开始时间 < 活动结束时间`；不允许零长度报名期，页面时间统一按 Asia/Shanghai 展示并以系统时间判断边界 `[ASSUMPTION A-4]`。

按 A-4 的建议，时间条件在服务端执行业务状态变更时判断，不能仅信任页面按钮或客户端传入时间。

## 4 功能需求

### 4.1 账号

#### FR-01 注册与登录

用户可注册并登录，获得本人身份。初稿建议使用唯一用户名、昵称和密码，不收集手机号、学号或实名资料 `[ASSUMPTION A-5]`。

- 相同用户名不能注册两个账号；缺少必填项或凭据错误时不建立登录状态。
- 注册成功的用户均可创建活动；不存在“先申请组织者资格”的隐含门槛。

#### FR-02 退出登录

用户可退出登录。

- 退出后，原登录凭据不能继续执行报名、创建或审核等需登录操作。
- 客户端保留旧页面也不能绕过服务端身份校验。

### 4.2 活动发布

#### FR-03 创建与修改草稿

登录用户可创建、保存和修改自己的活动草稿。初稿字段为标题、说明、地点、容量、报名起止时间、活动开始时间和报名模式 `[ASSUMPTION A-4]`。

- 容量为 0、负数或非整数时不能发布；必要字段缺失时不能发布。
- 按 A-4 的建议，报名开始等于或晚于截止、截止晚于活动开始、结束不晚于开始时均拒绝发布；报名截止等于活动开始允许，但不会留下截止后的审核窗口。
- 他人不能读取或修改草稿；草稿不出现在公开的已发布活动列表。

#### FR-04 发布及模式固定

活动发起者可发布合法草稿，并选择一种报名模式。

- 发布后活动出现在已发布列表，报名方式可见；草稿不能接受报名。
- 已发布活动即使还没有报名记录，也不能切换模式；直接请求服务端同样不能修改。

#### FR-05 活动列表与详情

用户可查看已发布活动的标题、说明、地点、发起者、时间、模式、容量及剩余名额。

- 报名未开始、已截止或满额时显示相应原因；审核活动满额不等同于停止接收申请。
- 详情中的剩余名额以报名成功数计算，不能减去待审核人数；不公开完整报名名单。

#### FR-06 已发布活动的修改边界

初稿建议仅草稿可编辑，已发布活动的内容、容量与时间均不再修改；本版不提供删除或取消活动功能 `[ASSUMPTION A-4]`。

- 若采用该建议，发布后任何编辑或删除请求均不改变活动及报名记录。
- 用户若需要活动改期或取消，应先修订本条并评估已报名用户的处理方式，不允许实现时临时补规则。

### 4.3 两种报名模式

#### FR-07 先到先得报名

登录用户在报名期内可报名已发布的先到先得活动。

- 有剩余名额时产生报名成功记录，占用一个名额；没有名额时失败且不新增成功记录。
- 同一用户已有待审核或报名成功记录时不新增第二条有效记录；重复操作遵循 FR-17。
- 报名开始前、报名截止时及以后，均不能新报名。

#### FR-08 提交审核申请

登录用户在报名期内可对审核模式活动提交申请。

- 提交成功后为待审核，不是报名成功，也不占名额。
- 即使剩余名额为 0，仍可提交待审核申请；有人取消或释放名额时，不自动转为通过。
- 报名截止后不再接收新申请，但不因此删除此前提交的待审核记录。

#### FR-09 发起者查看申请

活动发起者可查看本人审核活动的申请及其状态。

- 仅看到自己活动的待审核、报名成功、已拒绝及已撤回等记录；他人活动不在管理范围。
- 待审核人数和报名成功人数分别显示，不能把全部申请数当成已报名人数。

#### FR-10 审核通过

活动发起者在审核期内可通过待审核申请；每次通过仍受容量约束。

- 报名截止后、活动开始前，仍可通过此前提交的申请；活动开始时及以后不能通过。
- 有名额时，待审核转为报名成功，只占用一次名额；并发处理不超出容量。
- 初稿建议容量不足时操作失败、记录仍为待审核，向发起者说明名额不足 `[ASSUMPTION A-3]`。

#### FR-11 审核拒绝

活动发起者在审核期内可拒绝待审核申请。

- 拒绝后状态为已拒绝，不产生成功报名，也不改变已占名额；报名者能查看结果。
- 初稿不强制填写拒绝理由；活动开始后不得再拒绝，已通过记录不能通过“拒绝”操作取消 `[ASSUMPTION A-3]`。

### 4.4 撤回、取消与重复操作

#### FR-12 撤回待审核申请

初稿建议报名者在活动开始前可撤回本人的待审核申请，包括报名截止之后 `[ASSUMPTION A-3]`。

- 撤回后为已撤回，名额不变；发起者不能再通过该条已撤回记录。
- 撤回与审核并发时不得出现“已撤回却占有名额”或一条记录同时处于两个当前状态；若审核先成功，用户须按 FR-13 取消。

#### FR-13 取消成功报名

已确认成功报名取消后释放名额；初稿将允许取消的时限定为活动开始前 `[ASSUMPTION A-3]`。

- 取消后状态为已取消，释放恰好一个名额；重复取消不额外增加剩余名额。
- 报名截止后释放名额也不延长报名期；审核模式仍可在审核期内处理此前提交的申请。

#### FR-14 再次报名与历史

初稿建议已拒绝、已撤回或已取消后，在报名期内可重新报名或申请，并保留前次处理历史 `[ASSUMPTION A-3]`。

- 新一轮仍按活动原有模式和当时容量处理；不能利用重新申请绕过报名截止。
- 同一用户对同一活动最多存在一条当前待审核或报名成功记录；历史成功但已取消的记录不继续占位。

#### FR-15 查看本人记录

用户可查看本人报名和申请的活动、当前状态与结果。

- 待审核明确提示“尚未报名成功”；已拒绝、已撤回、已取消不得显示为成功。
- 活动开始后仍未处理的申请保留可查，并提示审核已截止；不要求自动批准、候补递补或后台清理。

#### FR-16 查看活动成功名单

活动发起者可查看本人活动当前报名成功的用户名单。

- 该名单不含待审核、已拒绝、已撤回、已取消记录；人数与详情的已占名额一致。
- 初稿仅向发起者展示用户名、昵称和报名状态，不展示密码或其他账号私密信息 `[ASSUMPTION A-5]`。

#### FR-17 重复请求与失败反馈

系统应对重复点击、失效操作和业务失败返回明确结果，不因重复请求产生重复状态变化。

- 活跃记录的重复报名或申请返回已有状态或明确的重复提示，不新增一条活跃记录；重复通过或取消不重复扣减或释放。
- 未登录、无权操作、非当前状态、时间已过、容量不足等失败均不改变业务数据；报名者和发起者看到的结果不能互相矛盾。
- 状态冲突时返回当前状态，要求用户刷新后选择仍有效的操作，不把失败伪装为成功。

## 5 状态与边界走查

以下仅为验证规则的测试场景，不是已完成测试或来自真实使用者的旅程记录。

| 场景 | 应有结果 |
|---|---|
| 先到先得只剩 1 位，两位不同用户同时报名 | 最多一位新增报名成功，其余失败；剩余名额不为负 |
| 审核模式已有 10 条待审核、容量为 1 | 待审核不占位；只能通过一位，其他不会自动通过 |
| 审核模式满额时有新申请 | 接收为待审核；成功名单和已占名额不变 |
| 截止前申请，截止后但开始前审核 | 允许；到活动开始时间后禁止处理 |
| 他人伪造活动或申请标识提交审核 | 拒绝；数据不变，不泄露完整名单 |
| 重复通过、取消，以及撤回与通过并发 | 符合 FR-10、FR-12、FR-13、FR-17；取消和撤回细则须先确认 A-3 |

## 6 非功能需求

### NFR-01 名额与状态一致性

任意成功响应后的状态必须满足第 3 节不变量，失败操作不产生部分扣位或半成功状态。

验证建议 `[ASSUMPTION A-6]`：在每轮重置数据的条件下，以 50 个并发请求争抢最后 1 位，先到先得和审核通过各重复 20 轮；另外并发重复处理同一条记录，并交错执行通过、撤回与取消。每轮核对当前状态、成功记录数和剩余名额，超额、负名额、重复占用或重复释放次数必须为 0。测试报告记录实际环境、请求数、轮数及失败响应，不以请求全部成功为目标。

### NFR-02 身份与资源隔离

注册或登录不赋予管理他人活动的权限。密码不得以明文保存或出现在日志、名单及接口响应中；具体认证、密码保护和会话实现由架构决定。

验证：使用未登录用户、报名者、活动发起者、另一活动发起者直接请求各类管理、审核、个人记录和名单操作。未经授权的写操作成功数及他人私密记录泄露数必须为 0；退出后原凭据不能继续写入。每类允许及拒绝路径都保留验证证据。

### NFR-03 状态持久性与可复现

初稿建议：已经明确返回成功的注册、活动发布、报名、审核及取消结果，刷新页面或正常重启应用后保持一致，不能恢复到示例初始数据 `[ASSUMPTION A-7]`。

验证建议同属 A-7：保存含各种状态的数据，正常停止并重启，再比较用户、活动、当前状态、成功名单及容量，不得丢失已确认数据；异常断电恢复暂不列入目标。另按课程要求，由另一位成员从干净检出开始按 README 初始化、启动并运行验证，不假设其已有本机未提交配置。

## 7 成功指标与取舍

- **SM-01 核心行为正确**：FR-01 至 FR-17 的适用验收条件全部通过；依赖假设的条件须先由用户确认后才能计为通过。目标是可复现的正确结果，不是页面数量。
- **SM-02 名额正确**：NFR-01 指定验证中不变量违规次数为 0，同时说明实测条件；测试通过不等于证明所有运行条件均无缺陷。
- **SM-03 权限正确**：NFR-02 的未经授权写入和信息泄露均为 0；允许路径也必须能正常完成。
- **SM-04 真实可用性**：争取至少 1 位潜在发起者和 1 位参与者试用并记录结果与反馈；这是尚未完成的目标，不写成已经获得用户认可。

反向约束：不追求审核通过率、报名总量或待审核数量越高越好；不能为了让数据好看而把待审核计为成功、隐藏失败请求或省略权限检查。

## 8 第一版边界与课程约束

两种模式、正确占位、可见状态与资源权限属于核心范围。建议不做支付退款、短信或微信通知、小程序、原生移动应用、自动候补、多级审批、会签、自定义审批流程、积分签到、推荐、大型多租户平台及分布式高并发部署；这些是控制两人工期的范围建议，尚未逐项经过用户批准 `[ASSUMPTION A-8]`。活动编辑、删除与取消的额外限制另按 A-4 审阅。

项目截止日为 2026 年 12 月 9 日，实际为两人。正式史诗与至少 12 个故事在架构后拆分；本稿不提前指定技术栈、数据库事务或接口方案。后续建立 FR、ADR、故事与测试的编号引用。实验 A、两次冲刺、真实决策日志、AI 声明等继续作为课程过程要求管理，实验 B 按老师说明不做。

过程采用完整方案设计路径并按规模裁剪：课程要求 PRD、ADR 和多史诗故事，两种模式又共享容量与状态，因此保留架构、就绪检查和冲刺规划；两人短周期下，不增加企业审批流程或额外模块。是否完成这些过程由实际产物和提交记录证明。
